# AUDIT：样本有效性 — Q-1/Q-2/Q-3 裁决 + 样本可扩的真实路径

> 结论会让前几轮所有胜率数字**失去统计效力** —— 但那不是坏消息，因为样本本身并不缺。

## 1. Q-1 裁决：`capital` 不定位为打板策略

### 1.1 判据

「打板」意味着：以涨停封板价排队买入。它**不可自动化、不可回测**（成交与否取决于盘口排队与撤单速度，
日线数据完全无法表达）。把 `capital` 定义为打板策略，等于把它排除在「可回测、可迭代」的范围之外 ——
与这个项目「用数据迭代」的根本前提冲突。

### 1.2 裁决

| 环节 | 定义 |
|---|---|
| 信号 | 维持现状：资金流（净流入 / 连续天数）驱动，**这是有效信号，不改** |
| 入场 | **改为 T+1 开盘价执行**（不再用 T 日收盘价） |
| 出场 | 按 `PLAN-validation-fill-model.md` 方案②（目标价 / 止损价触发） |

副作用必须承认：**T+1 高开会吃掉一部分涨幅**，`capital` 的收益会显著低于现在看到的 +3.41%。
但那才是能拿到的收益。

### 1.3 技术可行性（有个坑）

`fetch_window_series`（`src/commands/backtest_validation.rs:412-416`）只取了三个序列：

```rust
let closes: Vec<f64> = valid_klines[..n].iter().map(|k| k.close).collect();
let highs:  Vec<f64> = valid_klines[..n].iter().map(|k| k.high).collect();
let lows:   Vec<f64> = valid_klines[..n].iter().map(|k| k.low).collect();
```

**没有 open**。而 Q-2 的「T+1 开盘执行」和 R-2 的「跳空越价按更差价格」都依赖开盘价。

⇒ 实施前必须先确认底层 K 线结构是否有 `open` 字段并接通（`build_pick_validation` 的入参
从 3 个序列扩到 4 个，签名连带变化）。

## 2. Q-2 裁决：按 T+1 开盘价折算，不剔除

### 2.1 为什么不剔除

`PLAN-validation-fill-model.md` 的 R-4 原写「涨停入场样本不计入盈利能力分母」。按这个口径，
`capital_short` 40 单里 29 单被剔除，**只剩 8 单** —— 在只有 8 单的情况下任何结论都不可信。

### 2.2 折算更优的理由

| 维度 | 剔除 | **折算（T+1 开盘）** |
|---|---|---|
| 样本保留 | 丢 78%（29/40） | **全保留** |
| 可执行性 | 承认买不到，但丧失评估能力 | **T+1 开盘是真实可执行的** |
| 信息量 | 只回答「打板赚不赚」 | 回答「这个信号值不值得追」 |
| 对高开的惩罚 | 无（直接扔掉） | **自动体现**（高开吃收益） |

⇒ 涨停入场不是「不可执行」，只是「T 日收盘不可执行」。**T+1 开盘仍可执行** —— 这才是应该度量的东西。

### 2.3 仍需剔除的残余

**一字板**（T+1 开盘即涨停且全天未打开）确实买不进。判据（有 OHLC 后即可算）：

```
open == high == low 且 open >= prev_close × 1.098（主板）/ 1.198（创业板科创板）
```

这类样本标 `unfillable_limit_up`，不进盈利能力分母。预计数量远小于 29 单。

## 3. Q-3 裁决：trend/value 全负不是策略问题

`trend_short −1.68%`、`trend_ultrashort −1.57%`、`value_ultrashort −0.89%` 曾被当作
「这些策略不行」。取证后发现是三个测量缺陷叠加，其中任何一个都足以让数字失去意义。

### 3.1 缺陷一：批次独立性 —— 127 单实际只有 **7 个独立观测**

| 格 | 样本 n | **批次数** | 日期 |
|---|---:|---:|---|
| capital_short | 40 | **4** | 08-01, 09-11, 09-12, 09-27 |
| capital_ultrashort | 30 | **3** | 09-12, 09-13, 10-09 |
| trend_short | 12 | **2** | 08-01, 09-27 |
| trend_ultrashort | 6 | **2** | 09-13, 10-01 |
| value_short | 29 | **3** | 08-01, 09-12, 09-27 |
| value_ultrashort | 10 | **1** | 09-13 |
| **合计** | **127** | **7 个不同日期** | 08-01 ~ 10-09 |

**同一批次里的票共享同一天的市场环境 ⇒ 高度相关，不是独立样本。**

⇒ `trend_short −1.68%` 是「**2 个市场日**的结果」，不是 12 个证据。
⇒ `value_ultrashort −0.89%` 是「**1 个市场日**的结果」，统计上等于零信息。

**所有此前的标准误（如 40.9% ± 4.4%）都按 n=127 算 —— 严重低估了不确定性。**
真实有效样本量接近**批次数（≈7）**，不是单数。

### 3.2 缺陷二：验证覆盖缺失 —— 数据在库里，只是没跑

`reco_picks` **26,087 行 / 28 个交易日**（2026-07-31 ~ 10-24），但 `decision_validations` 只有 1,654 行（6.3%），
且成熟 judged 样本只覆盖其中 8 天。

按日期看验证覆盖率：

| 日期 | picks | 已验证 | 覆盖率 | 有判定 |
|---|---:|---:|---:|---:|
| 08-01 | 371 | 174 | 46.9% | **116** |
| 09-11 | 226 | 126 | 55.8% | **20** |
| 09-12 | 370 | 180 | 48.6% | **60** |
| 09-13 | 240 | 168 | 70.0% | **56** |
| 09-27 | 247 | 174 | 70.4% | **46** |
| 10-01 | 424 | 36 | 8.5% | 6 |
| 10-09 | 692 | 324 | 46.8% | **42** |
| 10-12 | 535 | 126 | 23.6% | **21** |
| 10-13 | 434 | 0 | **0%** | 0 |
| 10-17 ~ 10-24 | 24,265 | 124 | **0.5%** | **0** |

⇒ **2026-10-13 之后基本没有验证**（10-17~10-24 共 24,265 条 picks，0 条有判定）。

这不是「样本攒不出来」，是「**样本在库里但没跑验证**」。

### 3.3 缺陷三：数据重复 —— 同一候选被写多次

**`reco_picks` 层面**（10-19）：

| 指标 | 值 |
|---|---:|
| 行数 | 13,431 |
| 唯一 `id` | 13,431 |
| **唯一业务键**（stock+style+period+小时） | **4,681** |

⇒ 同一候选平均重复 **2.9 次**，单格最多 **30 次**（600707 / trend / short）。
没有业务唯一约束，重跑/重扫就插新行。

**`decision_validations` 层面**（127 单）：

| 格 | 行数 | 唯一样本 | 重复行 |
|---|---:|---:|---:|
| capital_short | 40 | 37 | 3 |
| capital_ultrashort | 30 | 27 | 3 |
| trend / value 四格 | 57 | 57 | 0 |
| **合计** | **127** | **121** | **6** |

⇒ 127 单里 **6 行是重复**（4.7%），且全部集中在 `capital`（与 reco_picks 重复写入同源）。
如 `600088` 在 `capital_short` 里出现两次，价格、收益、判定**逐字段相同**。

重复比例不大，不改变结论方向；但它说明**「样本唯一性」这一层此前无人校验**。

### 3.5 重复的真实结构：不是「一次调用写重了」，是「同一任务跑了 32 次」

原计划给 `reco_picks` 加 `(stock_code, style, period, generated_at)` 唯一约束 —— **取证后判定不可行**。

**证据链（2026-10-19）**：

| 观察 | 值 |
|---|---:|
| 该日总行数 | 13,431 |
| **批次数**（`count(DISTINCT generated_at)`） | **32** |
| 每批行数 / 批内唯一键数 | **440 / 440**（批内干净，无重复） |
| 同一票 32 批的 `pick_data` md5 | **全部相同**（`c0b68cec…`） |
| `confidence` / `synthetic` | 全部相同（40 / 1） |

⇒ **同一逻辑任务在 20 分钟内被执行了 32 次，每次都写了一模一样的 440 行。**
时间戳证据：`06:08:41.903` 与 `06:08:42.046` 相差 0.14 秒；
`06:11:04.253` / `04.912` / `06.641` / `07.174` 在两秒内跑了四次。

**为什么「唯一约束」挡不住**：`generated_at` 精确到毫秒且每次运行都不同
⇒ `(stock, style, period, generated_at)` 的每个组合**本来就唯一**。
要挡住它必须把时间截断到日，但那会禁止「同日多次合法刷新」—— 语义上是另一个决策。

**⇒ 改为在验证链去重**（不动写入路径、不动 DDL）：
按 `(stock_code, style, period, 日期, as_of_date)` 只验证一份、保留最新批次。
写入侧的重复属独立问题（A-1b：触发源收口）。

### 3.6 附带发现：`synthetic=1` 兜底合成占 72~100%

| 日期 | 行数 | 兜底占比 |
|---|---:|---:|
| 2026-10-17 | 1,760 | **100.0%** |
| 2026-10-01 | 394 | 98.5% |
| 2026-10-19 | 13,431 | 95.0% |
| 2026-10-13 | 434 | 94.5% |
| 2026-10-18 | 6,454 | 93.9% |
| 2026-08-01 | 226 | 84.1% |
| 2026-09-12 | 220 | 86.4% |

⇒ **荐股主链在大部分日期是以兜底合成状态运行的**（真实信号未产出，走降级路径）。
这是独立于本文的 P0，登记为 A-1c。

**但好消息**：127 单成熟样本 **全部 `synthetic=0`**（0 条兜底），
且 `backtest_validation.rs` 的 `exclude_synthetic` **默认 true** ⇒ 补验证会自动排除兜底。
所以这批样本本身没被兜底污染。

### 3.7 真正的根因：`backtest_validation.rs` 三缺陷叠加

读 `run_decision_backtest` 的选取段（`backtest_validation.rs` 通用通道）：

```rust
// 按 generated_at 倒序，优先回测最近的数据      ← 注释这么写
let picks = query.all(db).await...;              // ← 但没有 order_by！
let picks: Vec<_> = picks.into_iter().take(max_picks as usize).collect();  // ← 也无去重
```

| # | 缺陷 | 后果 |
|---|---|---|
| 1 | **注释说倒序，代码没有 `order_by`** | 取到哪 200 条由数据库返回顺序决定 —— 注释与实现不符 |
| 2 | `take(max_picks)` 默认 **200** | 28 天的真实 picks 远超 200 ⇒ 永远只覆盖少数日期 |
| 3 | **完全没有去重** | 同一票的 32 个批次各验证一次 |

⇒ 三者共同解释了「127 单只覆盖 7 个日期」+「6 行重复」。
**这不是数据脏，是取样逻辑有问题。**

> 注：`max_picks` 默认 200 本身仍是 A-2 的前置 —— 补验证必须显式传大值，
> 否则去重后依然只覆盖少数日期。

### 3.4 结论

`trend` / `value` 的负收益**不能归因于策略**。它们来自：

- 2~3 个市场日（`trend_short` 12 单来自 2 天）；
- 且验证覆盖严重不全（28 天里只有 8 天有判定）；
- 且存在 4.7% 的重复样本。

**在补齐覆盖、去重、并按批次重算置信区间之前，任何一格的胜率都不该用于决策。**

## 4. 样本可扩的真实路径（比回放便宜得多）

前几轮我把注意力放在「时间旅行回放」上。本次取证表明：**在回放之前，有一批几乎免费的东西没做。**

| 手段 | 成本 | 能加多少样本 |
|---|---|---|
| **补跑验证**：把 `reco_picks` 的 28 个交易日全部验证 | 低（现成命令 + K 线） | 判定样本可到**数千条**，单格数百 |
| **去重**：给 `reco_picks` 加业务唯一约束 | 中（DDL + 写入路径） | 提升样本纯度，不改量 |
| **修 R-4 / 方案②** | 中（open 序列 + 判定重构） | 不改量，改**可信度** |
| 时间旅行回放 | 高（见 `AUDIT-replay-sample-feasibility`） | 受限于选股层不可回放 |

⇒ **优先级应为：补验证 > 去重 > 改验证模型 > 回放。**

补验证之所以最关键：它同时解决「批次独立性」（28 天 = 28 个批次，而不是 7 个）
和「样本量」（数倍增长），且不需要任何新架构。
