## ADR-P4-1 — 配额只做运行维度，部门覆盖表，min 生效（D1=A、D2=A+C）

**决策**：`bot_department_quotas` 只存**运行配额**（并发/超时/步数/链每层在途/单步超时/同时在跑编排数），不做费用或 Token 配额。作用域为**部门**：仅 `bot_workflows.owner_scope='department'` 的编排及其运行子树受该部门配额约束；实例级编排与纯委派链继续用 P3 常量。生效值 = `min(定义值, 部门配额)`。

**理由**：P3 已把全部运行预算固化为常量且无用量账本（`GAP-P4` G-Q6）；运行配额是纯策略覆盖，不需要记账链路，可在 P4 内闭环。费用配额需要 Bot 维度 token/cost 归集，属独立工程。部门是现有唯一组织维度（`bot_departments` + 成员表），把配额挂部门无需引入新的 scope 体系。

**后果**：无配额行的部门行为与 P3 完全一致（`isDefault=true`）；删除部门时同事务删配额行，编排按 ADR-P3-3 转实例归属后不再受该配额约束（转实例即退出部门作用域，语义自洽）。跨部门编排（实例级）不受任何部门配额限制。

**反转成本**：若改为实例+部门通用表（D2=B），换表结构 +0.5 人日，多一层查询与 UI；若追加费用配额（D1=B），另立 P5，8–12 人日。

## ADR-P4-2 — 只收紧不放松，超额可见拒绝（D3=A）

**决策**：部门配额是**硬天花板**，不允许放大 P3 默认值（列级 CHECK 上限即 P3 默认：并发 1..4 中默认 2、总超时 ≤3600、步数 ≤12、每层 ≤4、单步 ≤900、同时运行 ≤8）。保存/更新定义时校验 `定义值 ≤ 配额`，触发运行时再校验一次；超额返回 `BOT_QUOTA_EXCEEDED`，detail 带字段名、定义值与上限。**禁止静默夹紧**。

**理由**：静默夹紧会让用户以为定义已保存为所见值，实际运行按别的值执行（R6）。拒绝 + 字段名是唯一可解释、可测试的行为。

**后果**：前端需把错误码映射到具体输入框；配额下调后已存在的超限定义在下次保存或触发时失败，但定义本身不被改写。`max_steps` 硬顶 12 与 P3 `bot_workflow_runner.rs` 上限一致，配额不能把它放大到 13。

**反转成本**：改为自动夹紧只需把校验替换为 `min` 并放弃错误码（A2 内 ≤0.5 人日），但需补「被夹紧」提示，否则重演 R6。

## ADR-P4-3 — 待答独立请求表，不改 assignment / run 状态机（D6=A）

**决策**：新增 `bot_input_requests` 承载待答生命周期 `pending → answered | expired | cancelled`；`bot_assignments` 五态与 `bot_workflow_runs` 状态**零变更**。请求行可选关联 `workflow_run_id` / `assignment_id`（为未来无人值守预留，D4=A 下恒 NULL）。

**理由**：改 assignment 状态机会牵动 P2-b/P3 的状态迁移、`TransitionPatch`、事件与全部断言（`bot_assignment.rs`、`bot_delegation_chain.rs`、e2e），收益仅是少一张表。独立表让待答可列举、可审计、可按会话恢复，天然支持刷新恢复。

**后果**：run 面板与 assignment 面板不显示「待答中」，待答只在 Bot 线程与 `/bots` 徽章可见；将来做无人值守需补「assignment 等待待答」的关联语义，但表结构已预留列。

**反转成本**：若改为状态机内态（D6=B），需扩两套状态机 + 迁移旧行 + 改 P3 断言，约 3–4 人日，不建议。

## ADR-P4-4 — 超时 300s，过期即错误终态（D5=A）

**决策**：`expires_at = created_at + 300s`（与 `AppAskUserBridge` 现行为一致，常量集中 `bot_input_request.rs`）；到期后行转 `expired`，等待方收到既有 `AGENT_INPUT_WAIT_REPLY_TIMEOUT`。过期行不可再答（`BOT_INPUT_REQUEST_NOT_PENDING`）。

**理由**：不改现有交互超时语义 = 通用聊天零回归；独立可配超时会引入第二套计时器与第二套错误口径。

**后果**：P4 不提供“可配超时”；`AGENT_INPUT_WAIT_REPLY_TIMEOUT` 的 zh-CN 文案已是用户可见的既有文案，无需新码。

**反转成本**：改为可配（D5=B）需加列 + UI + 计时器读值，约 +1 人日；默认答案（D5=C）会改变模型行为，不建议。

## ADR-P4-5 — 答复只投活轮，重启清扫过期（D7=A）

**决策**：`answer_bot_input_request` 只向当前进程内仍存活的 oneshot 投递；找不到活 sender 时返回 `BOT_INPUT_REQUEST_NOT_PENDING`（行已转终态或进程已重启）。应用启动时把上一进程遗留的 `pending` 全部置 `expired`（原因固定文案）。**不做断点续跑**。

**理由**：被中断的模型轮无法从中间恢复；把过期行标成“可答”会让用户点了没反应（R3）。清扫保证 UI 不出现幽灵卡。

**后果**：重启后进行中的交互 Bot 轮失败，用户需重新发问；这是 P4 明确的范围外（`PLAN-P4` §1.3）。

**反转成本**：若做答案暂存待续跑（D7=B），需持久化执行上下文与恢复协议，属新执行路径，不建议。

## ADR-P4-6 — needs_input 只覆盖交互 Bot 线程（D4=A）

**决策**：只有 `conversation_id` 指向 Bot 线程（`conversations.bot_id` 非空）且由人在场的交互轮会产生持久化待答行。例程/委派/编排等无人值守轮保持 P2-a `prompter=None` + 无提问桥，行为零变化。

**理由**：无人值守无回答者；扩面需要“等谁答、超时怎么办、要不要终止 run”的完整协议（+3–4 人日），且会推翻 P3 对 needs_input 的四条排除口径（`PLAN-P4` §0.3）。P4 先解决“人在场但刷新丢卡”的真实痛点。

**后果**：P3 四条排除口径继续有效，P4 不 supersede 其中任何一条；`origin`/`workflow_run_id`/`assignment_id` 列预留但不写值。

**反转成本**：扩到无人值守需 supersede P3 口径 + 加桥 + 加等待态语义，约 +3–4 人日，列为后续候选。

## ADR-P4-7 — 两条切片独立上线，同批交付（D8=A）

**决策**：P4-a（配额）与 P4-b（待答）互不依赖，各自有独立的实体、命令、前端与测试；同批提交但在收口判定中分别签字。若一条延期，另一条可单独收口并把延期项标 `deferred`。

**理由**：两条切片风险面不同（配额是策略层、待答是交互层），并行可缩短 6–7 个工作日的关键路径；独立签字避免一条拖死整批。

**后果**：`ACCEPTANCE-P4.md` 分 A/B 两节；INDEX 登记同一批文档；任一节的 FAIL 不影响另一节 PASS。

**反转成本**：若必须整批原子上线，只需把收口判定从“分节签字”改为“全绿才签”，零代码成本。

## ADR-P4-8 — 配额解析一次、经 task-local 下发（承接 R2）

**决策**：`resolve_workflow_limits(department_id, definition)` 在 run 创建时执行一次，得到 `QuotaLimits`；随后经 `AssignmentContext` 的 task-local 传给 workflow runner 与 assignment runner。子孙 assignment 不重复查库。无 `department_id`（实例级编排/纯委派）时直接返回 P3 默认常量，零 DB 读。

**理由**：配额若在每次派发热路径查库，会给 P3 已压测过的链式派发增加 DB 抖动（R2）；一次解析也保证同一 run 内所有步骤看到同一组上限，避免运行中途改配额导致前后不一致。

**后果**：run 创建后修改部门配额不影响在途 run（下一次触发生效）；`max_concurrent_runs` 只能在 run 创建前判定，已在跑的数量在创建时统计。

**反转成本**：若要求运行中即时生效，需在每次派发重解析，热路径成本 +1 次 DB 读/派发，不建议。
