## 0. 摘要：四条顶级结论

### 结论一：**「执行成功」这个信号本身已经失效**

| 证据                                                            | 数值                                    | 出处               |
| --------------------------------------------------------------- | --------------------------------------- | ------------------ |
| `workflow_executions` 中 `partially_completed` 占比             | **204 / 473 = 43%**                     | L2 实测            |
| `workflow_execution_stats` 中同状态占比                         | **142 / 261 = 54%**                     | L2 实测            |
| 上述「部分完成」行中带 `output_result` 的比例                   | **204 / 204 = 100%**（203 条 >50 字符） | L2 实测            |
| `daily-market-events` 状态标 `completed` 但产出是失败报告的比例 | 5 次执行中 **4 次产物不可用**           | L2 实测（见 P0-1） |

**这意味着**：库里任何以 `status` 为判据的统计（成功率、健康度、SLA）都不可信；前端把降级产物当正常结论展示，用户无从分辨。

### 结论二：**荐股产出的 81% 是合成假数据，且假数据排真实数据之前**

| 类别                    | 条数    | 平均置信度          |
| ----------------------- | ------- | ------------------- |
| `synthetic = 0`（真实） | **111** | 28.50（范围 1–100） |
| `synthetic = 1`（合成） | **480** | **恒定 40**         |

- 真实数据占比 **18.8%**；合成数据置信度恒为 40，**高于真实数据的平均值 28.50** → 排序/展示上假数据压过真数据。
- **11 个风格中只有 3 个能产出真实候选**：`capital`（short）、`value`（short）、`serenity`（mid）。其余风格（trend / reversion / technical / earnings / event / policy / watchlist / capital_flow / bottleneck）**长期全量靠合成兜底**。
- 2026-09-12 当日批次仍复现同一形态。

### 结论三：**决策链吃进了合成常量，且足以翻转 action**

- `factor_evidence` 的因子输入中，`chip` / `consensus` / `money_flow` 三项**全部是推荐层合成的常量 `50`**；
- `debate-convergence` 的 `bottleneck` / `px` / `technical` 无来源 → 以 `50` 参与「因子一致度方差」计算；
- `t-catalyst-data` 缺失时 alpha 回退 `DEFAULT_ALPHA = 1.0`；
- 合计对 posterior 影响约 **±0.075**；实测在 posterior ∈ [0.30, 0.468] 区间的 13 个样本中，该偏移**足以跨越「观望 / 减持」分档边界**。

**即：假数据参与了真实优化目标的计算，不是单纯的展示问题。**

### 结论四：**「买入」不可达的真因是「证据恒为负」，不是阈值、也不是仓位门**（已经过三轮更正 + 一次因子级归因，以此版为准）

> 且 f5 吃的是**破损估值计算的残骸**（`dcf.mid = 0` 却 `available = true`），不是真实「高估」。

### P0-4 荐股 81% 合成数据 + 合成置信度反超真实数据

见「摘要·结论二」。补充：

- 位置：`analysis-engine/src/recommender/strategies/watchlist.rs:213-380`（`emit_synthetic_picks` / `scan_synthetic_one`）、调用处 `mod.rs:740-780`、`group_by_style_and_trim`

- 合成条目标注的是**「信号缺失，按现价合成」**——即「无信号」被转化为「有推荐」。

**机制澄清（2026-09-12 深挖后修正）** —— 本条关系到改法，必须区分：

| 本报告原表述               | 实际机制                                                                                                                                                                                                                             |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 「synthetic 恒定 conf=40」 | 数值对，**但机制不是硬编码**。`calc_confidence(0.45, 0.4, 0.4, 0.0, 1.0)` 的**输入全部取自固定默认值**（`syn_conf_*` 变量未被真实因子覆盖）→ 输出恒定 40。**修法是让输入用真实值，不是改常量**                                       |
| 「合成条目未标注」         | ❌ **错误**：`RecoPick.synthetic: true` + `reasons[0]` 含「信号缺失，按现价合成」+ `risk_notes` 明写「本条为按现价合成的兜底结果」→ **三处已标注**                                                                                   |
| 「按现价合成」             | `price` **是真实的**（`client.get_quote(code)`，且已过滤 `is_st` 与 `price<=0`）。**不真实的只有 `entry_low/entry_high/stop_loss/target_price/position_pct`** —— 它们 = `price × 固定系数`（系数来自变量 `syn_*`，可调但恒用默认值） |

**「为什么不能为真实值」——分两类空桶（这是本条的核心判据）**：

| 空桶类型             | 成因                                                                            | 能否用真实值                         | 实证                                                                                                                                                                                 |
| -------------------- | ------------------------------------------------------------------------------- | ------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **(a) 数据不可用型** | 拉不到 K 线 / 财务 / 资金流 → 策略短路 `None`                                   | **不能**（用真实值会因同样原因失败） | —                                                                                                                                                                                    |
| **(b) 信号不达标型** | 数据拿得到，但策略条件苛刻（trend 要求 MA5>MA10 + 近 5 日高 ×0.97 + 量比 ≥0.8） | **能，且应该**                       | 2026-09-12 批次 `short` 下 `capital` 产出 **20 条真实候选**、`value` 10 条，而同期 `trend` **20 条全 synthetic**。`capital` 依赖行情+资金流且出得来 ⇒ 行情链可用 ⇒ `trend` 属 (b) 类 |

**⇒ 结论**：`synthetic` 目前把 (a)(b) 两类混为一谈，导致 (b) 类——**本可以算真实值的那一批**——被永久降级为假数据。改法见 `PLAN` B2。

### P0-11（**已降级为 P1**）仓位门「上限 < 门槛」的口径错配 —— 已修复，实测零行为变化

> ⚠️ **本条经历三次更正，最终定性以此版为准。**
> 曾写作「买入在算术上不可能 / 三重死锁」，经**代码复核 + DB 正算复现**后**推翻**：
> 其中②（求值顺序）与③（probe）**不成立**，① 成立但**被完全掩盖**。
> **「买入不可达」的真因见 §0 结论四**：`avg_signal` 恒 ≤ 0 ⇒ `effective_posterior` 上不去。

**成立的那部分（代码事实）**：

| 常量                                              | 值       | 位置                                                  |
| ------------------------------------------------- | -------- | ----------------------------------------------------- |
| `POS_BUY_MIN`                                     | **15.0** | `portfolio-mgr.rhai:125`                              |
| `POS_CAP_EXTREME` / `apply_risk_cap` 极高风险上限 | **10.0** | `portfolio-mgr.rhai:142` / `portfolio_formula.rs:223` |

⇒ 极高风险标的的 `position_pct ≤ 10 < 15`，「买入」的第二个门在该档下算术上不可能通过。
同一语义（风险仓位上限）在 Rust 与 Rhai **两处独立实现**（值恰好一致），属重复定义 —— 是隐患来源。

**为什么实际无影响**：`pm_risk_veto`（`portfolio_formula.rs:376`）对极高风险把 买入/增持/持有 **一律降级为观望**，该门的差异永远到不了最终 action。**门槛与 veto 构成冗余。**

**已实施修复（A + B，2026-09-12）**：

| 项         | 内容                                                                                                                                                                                                                                           |
| ---------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A 解耦     | 新增 `kelly_pos_uncapped = clamp(kelly_raw/2*100*(1-COST_PCT), 0, 95)`（`portfolio-mgr.rhai:1237`）= `apply_risk_cap` **之前**的值                                                                                                             |

**实测结论（`pg-p11-verify.js`）**：

2. **凡 `clip/clamp` 之外的「阈值判定」，都要问一句：判据是客观证据还是模型自评？**

3. **复算必须做模板版本对齐**：同一张表里跨版本记录混存，`score` 公式在 V67 / P1-B3
   两次变更 ⇒ **不按版本分组算残差，会得到一堆看起来像模型错误的残差**。
   本次 8 条 7 月记录的 −21 ~ −26 全是版本差异，若不做对齐会误判为「复算模型错了」。

**方法论沉淀（补充铁律 6）**：**「取值函数」本身也会成为静默失效点**。
`bb_str` 这个名字听起来是「安全取值」，实际上它内含了「值必须是字符串」这个**未声明的契约**；
一旦上游把值换成对象（LLM 信封化 / API 追加元数据），**所有调用点同时静默归零**，
而调用点本身看起来毫无问题。**检法**：对每个「通用取值 helper」，dump 一次它将要读的
**真实值类型分布**（`typeof` / `kind`），而不是只检查「键是否存在」。

**方法论沉淀 2（补充铁律 3 的姊妹条）**：**「接线缺失」与「契约漂移」是两种不同的失效，处置方式相反**。
L1/L2/L4 是**接线缺失**（数据在 bb 里、代码没接上）⇒ 改代码即可；
L3 是**契约漂移**（模板早已不产出这些键，但下游命令签名还留着这 5 个参数）⇒
**改代码无解**，只能补数据源或删参数。**判据：把「命令签名声明的参数」与「本版本模板实际落库的键集」并排比对，
差集非空即为漂移** —— 这一步本可在 `bb_json` 返回空串时顺带打印，成本极低。

> **⚠️ 二次取证后的修正（2026-09-12 下午，L3 落地时）**：上面「L3 只能补数据源或删参数」**说得太绝对**。
> 用 `pg-p0h-nodes.js` 展开 `raw.combined` 后发现 **14 个 `node_id`**，其中 `t-lockup-data.content.block_trades`
> **本来就有 8 条真记录** ⇒ 「键不存在」其实是**「取值路径对不上」**（命令读扁平点号键、模板产出**聚合器信封**）。
> 这类**改代码可解**。**所以「契约漂移」要再分两型**：
> ① **路径漂移**（键在，但层级/信封包装不同）⇒ 改取值路径即可；
> ② **真缺失 / 语义错**（模板确实不产出该键，或产出的东西语义不对）⇒ 只能补数据源或删参数。
> 判据升级为：**先 dump 上游聚合器的完整 `node_id` 清单与各自键集，再做差集** —— 只看「命令签名 vs bb 顶层键」
> 会把①型误判成②型（本轮初判即栽在这里）。**且「数据源可用」≠「语义正确」**：`get_peers` 接口是活的，
> 返回的却是概念板块（603353 ⇒ 高压快充/存储芯片/先进封装），冒充「同行业」⇒ 这类只能删。
