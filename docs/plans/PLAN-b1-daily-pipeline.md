## 3. B1-1：放开 maxPicks

### 3.1 改法

`cron_jobs.data` 是 text 列里的 JSON，改 `prompt` 字段：

```json
{ "tPlusNList": [2, 5], "excludeSynthetic": true, "maxPicks": 3000,
  "dryRun": false, "periodFilter": null }
```

**为什么显式写 `tPlusNList`**：现在传 `null` ⇒ 代码默认跑 **2/5/28/90 四个窗口**。
而 `mid`(28) / `long`(90) 当前**一条都不会成熟**（行情止于 10-23，最老批次只有 54 个交易日），
白跑还写满 `insufficient`。**只跑 2 和 5**，`28/90` 等 12 月再开。

### 3.2 负载评估（改之前必须算）

- 每日真实票 20~70 条，去重后取上限
- 每条 2 个窗口 → **每日 40~140 次取数**
- 现有并发上限 8、单票超时 10s ⇒ 最坏 ~3 分钟，`timeout_seconds=300` **刚好够，但没有余量**

⇒ 建议同时把 cron 的 `timeout_seconds` 从 300 提到 **900**，否则放开了也会被超时截断。

### 3.3 验收（每天看，不看总量）

```sql
-- 每日新增判定行数，应稳定在 20+ 且非 0
SELECT left(generated_at,10) AS d, count(*) AS judged
FROM decision_validations
WHERE hit_outcome IN ('hit','miss','partial','false_hit')
  AND ((period='short' AND t_plus_n=5) OR (period='ultrashort' AND t_plus_n=2))
GROUP BY d ORDER BY d DESC LIMIT 14;
```

**判据**：连续 5 个交易日 `judged ≥ 20`。若某天为 0，查是「没出票」还是「出了没验」——
两者处方完全不同（前者是荐股链，后者是本任务）。

## 4. B1-2：因子台账（与 B-3 的 F-1/F-2 是同一件事）

### 4.1 记录什么（**已按实际类型修正**）

`PickValidation.factor_snapshot` 的实际类型是 **`Option<HashMap<String, f64>>`**
（`hit_rate_backtest.rs`），即**扁平 map、只有数值、不能嵌套**。
所以不能像初稿那样写嵌套 JSON 或字符串版本号。修正后的快照：

```json
{
  "chg1": 3.42,           // 当日涨跌幅(%)
  "dist_lo20": 12.7,      // 距 20 日最低收盘价的涨幅(%)
  "rev20": 8.1,           // 20 日累计收益(%)
  "posshare20": 55.0,     // 20 日上涨天数占比(0~100)
  "factor_version": 1.0   // 口径版本（数值，非字符串）
}
```

**`quintile` / `score_pct` / `universe_n` 不在快照里** —— 分位需要**当日全市场横截面**
（约 5,500 只），单票路径拿不到；硬算只能伪造分母。
⇒ 分位由下游在横截面上用 SQL 另算（`market_daily_close` 已含全市场收盘价）。
这是初稿的一个设计错误，已修正。

**决策日不落进快照**（无字符串位）：约定为 `left(generated_at, 10)`，
即「`trade_date <= 决策日` 的最后一根 bar」。该规则确定且可复现，写入模块文档。

### 4.2 为什么必须落在 `factor_snapshot` 而不是新表

- 字段已存在（text/json），`hit_rate_backtest.rs` 里现在硬编码 `None`（`:616` 附近，TODO 未实现）
- 与 `decision_validations` 天然同行同生命周期，不需要 join、不需要迁移
- `AUDIT-factor-evidence` §7 的 F-2 就是这一条

### 4.3 实现要点（Rust）

| 步骤 | 说明 |
|---|---|
| 1 | 在 `analysis-engine` 新增 `factors.rs`：**纯函数** `compute(series: &[Bar], as_of_idx) -> FactorSnapshot`，输入已截断到截止日，函数内不做任何 IO |
| 2 | `backtest_validation.rs` 取数时**额外取 30 个交易日的回溯窗口**（当前 `fetch_window_series` 只取 T+N 前向窗口，没有回看） |
| 3 | 用回溯窗口算因子 → 序列化进 `factor_snapshot` |
| 4 | `factor_version` 常量固定为 `"v1"`，将来改因子定义必须升版（与 `RECO_ALGORITHM_VERSION` 同理） |

**关键纪律**：因子必须在**截断后的序列**上计算。若把全量行情传进去再按索引截断，
任何跨索引的窗口统计都会看到未来 —— 这是 `AUDIT-replay-sample-feasibility` 已识别的前视偏差模式。

### 4.4 历史 308 条能否回填

能。因子只依赖 `market_daily_close` 的历史收盘价，而 2026-06 起密度完整，
308 条的入场日全部 ≥ 07-31 ⇒ **回溯窗口齐备**。
⇒ 回填可用同一个纯函数、传「截断到入场日」的序列，与实盘路径共用一份实现。

## 6. 60 天能不能拿到

按每日真实票 20~70 条、去重后约 **30 条/日** 估算：

| 项 | 值 |
|---|---|
| 每日独立入场日 | 1 |
| 60 个交易日样本 | ≈1,800 条 |
| 独立批次 | **60** |
| 可检测 α（T+5，日残差 sd 1.39pp） | **≈0.5pp** |
| 因子 IC 的 t 值（7→60 天） | 约 ×2.9 |

⇒ **60 个交易日后，`AUDIT-factor-evidence` 里那些 t≈2.5 的结论才能从「推测」升为「证据」。**

**所以 B1-1 与「荐股链降级归因」是绑定的**（后者是已登记的独立 P0）。

### 10.1 更正一：`maxPicks` **不是**瓶颈（§1.1 / §3 作废）

按**业务键**（`stock_code × style × period × 决策日`，`period` 已归一化）核对真实票的验证覆盖率：

| 档 | 真实票键数 | 已验证 | 缺失 | 覆盖率 |
|---|---:|---:|---:|---:|
| short | 206 | 204 | 2 | **99.0%** |
| mid | 157 | 142 | 15 | 90.4% |
| ultrashort | 134 | 123 | 11 | 91.8% |
| long | 101 | 99 | 2 | 98.0% |
| **合计** | **598** | **568** | **30** | **95.0%** |

**⇒ 积压已经清完。** 剩下 30 个键缺失的主因是**持有期未成熟**（mid/long）
或最近几日的 T+N 前向 bar 不足，不是取数上限。

而待验证的真实 pick **只有 157 个 id**（< `maxPicks` 默认 200），
放开到 2000 **一条也多不出来**。

⇒ **B1-1 不必做。** 原判断「`maxPicks` 是 127 单只覆盖 7 天的第二个成因」是错的：
真正的原因是 A-1 修掉的**缺 `order_by`**（无序取前 200）。A-1 已经解决。

⚠ **AGENTS 教训**：我上一版把 `written=0 skipped=20` 读成「只处理了 20 条」。
`skipped` 是「已存在故跳过」，不是「取样上限」。**用 skipped 反推取数上限是错的。**

⚠ **口径教训（差点报错）**：第一次按 `USING(period)` join 得到
「`ultra_short` 134 条真实票、0 条验证」，看起来像 P0 漏验。
实际是 **D-2 值域不一致**（`reco_picks='ultra_short'` vs `decision_validations='ultrashort'`），
`replace(period,'_','')` 归一化后覆盖率立刻变成 91.8%。
**跨表 join 前必须先验值域，否则会造出一个不存在的 P0。**

### 10.2 更正二：`synthetic` 不是「供应商故障兜底」（§1.2 作废）

代码实证：`synthetic=1` 的语义是**「入场价是占位值，不是信号推导」**，
不是「调供应商失败重试」。

- `capital.rs:222`：「本分支是**降级占位**（无资金流，仅量价代理）⇒ 恒 `synthetic: true`；
  这是『没有资金流就不冒充资金驱动』的如实标注，**不得改成 false**」
- `watchlist.rs` 文件头：本桶出票默认 `synthetic: true`（入场位是现价乘数）
- `mod.rs:1379/1463`：**空桶会被 `emit_synthetic_picks` 按现价合成占位填满**，
  日志 `bucket was empty, filled with N synthetic picks`

**⇒ 73~95% 的合成率意味着「各信号腿大部分时候不出票」，不是「链路崩了」。**

### 10.4 更正四：60 天拿不到 §6 说的功效（最关键）

§6 只算了「批次数 60 ⇒ 可检测 0.5pp」，**漏了一个量纲**：
**每日票数决定了「当日 α 的估计噪声」**，而批次功效取决于这个噪声，不是取决于总样本数。

日级 α 的方差 ≈ 个股噪声 / 当日票数 + 市场级残差：

| 每日票数 | 日级 α 标准差（估） | 60 天 SE | **可检测 α（80% 功效）** |
|---:|---:|---:|---:|
| 30（原假设） | ≈1.4pp | 0.18pp | **≈0.5pp** |
| **6~7（实测）** | **≈5.7pp** | 0.74pp | **≈2.1pp** |
| 24 | ≈2.9pp | 0.37pp | ≈1.0pp |

（估算口径：个股收益 sd ≈14pp；日级 α sd ≈ √(14²/n + 1.4²)）

**⇒ 在日均 6~7 票的现实下，60 天只能排除 α > 2pp 这种大本事，
测不了 0.5pp。要达到原目标，要么把每日真实票提到 24+ 条，要么等 240 个交易日。**

**这条把优先级彻底改了**：与其「攒天数」，不如**把每日真实票数做上去**。
而做上去的手段只有三个：
① 修资金流通道（恢复 `capital`，历史上它是净收益最好的格）
② 定性那 6 个从未出票的风格（可能只是没接线）
③ 放宽现有腿的出票条件（**会改变生产输出，必须预注册**）

| MA 金叉 | `if fast <= slow { return None }` | 不受影响 |
| 站上锚均线 | `if last < anchor * ma_tol { return None }` | 不受影响 |
| **量比** | `if amount_ratio < amt_min { return None }`，`amt_min=0.8` | **回落到 1.0 ⇒ 放行** |
| 破高点（可选） | `if last < high_n * high_tol { return None }` | 不受影响 |
| MACD（可选） | `if dif <= dea { return None }` | 不受影响 |

量比的实现是：

```rust
let avg_amt = indicators::avg_amount_n(&klines, w.amount_window).unwrap_or(0.0);
let turnover_anomaly = if avg_amt > 0.0 { today_amount / avg_amt } else { 1.0 };
```

**⇒ `amount` 全为 0 时量比回落到 1.0（> 0.8）⇒ 不会卡住 `trend`。**
我一度怀疑「成交额全零串起了腿空 + 因子缺失」，**这条猜测被代码否掉了**，登记以免后人重走：

> ⚠ 不要把 `amount=0` 当成「腿不出票」的原因。`trend` / `capital` 的量比都有 1.0 兜底。

**`trend` 真正的原因**：10-19~10-23 是下跌段，`fast <= slow`（均线空头排列）对绝大多数票成立
⇒ 趋势跟随策略**正确地**一只都不选。这不是 bug，是策略在下跌市里的应有行为。

### 10.7 由此得到的结构性结论：**采样是被 regime 选择的**

| 风格 | 产出与市场状态的关系 |
|---|---|
| `value` | 全天候（10-22 在 long/mid/ultra_short 三档都满额） |
| `reversion` | 下跌市更活跃（10-22 只有 short 档满额） |
| **`trend`** | **只在上涨段出票**（10-22 全空，10-21 才 5 条） |
| `capital` | 依赖资金流通道（10-22 全空） |

**⇒ 这不是「样本不够」，是「样本被市场状态挑过」。**
60 个交易日的积累里，`trend` 的样本只会来自其中的上涨段，
而用「上涨段样本」评价一个趋势策略，结论必然偏乐观。

⚠ **这一条比 §10.4 更严重**：即便把每日票数做上去，
只要样本在 regime 上是**非随机**的，任何胜率/IC 读数都带着选择偏差。
⇒ B1-3（IC 监控）必须**按入场日的市场状态分桶**再报，否则会和 §9.5 的 `chg1` 一样被时间混淆骗一次。
