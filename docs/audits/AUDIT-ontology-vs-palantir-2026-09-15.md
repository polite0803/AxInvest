## 1. 对照基准（Palantir Ontology 的工程事实）

### 1.1 三层模型

| 层                         | 回答              | 构件                                                             |
| -------------------------- | ----------------- | ---------------------------------------------------------------- |
| **语义层** Semantic        | 世界里有什么      | Object Type · Property（含 Shared Property）· **Link Type** · Interface |
| **动力层** Kinetic         | 数据怎么被"水化"  | 接入 → 管道 → **映射到 Object Type**；**数据血缘**；多源融合；批流统一 |
| **动态层** Dynamic（动词） | 谁能改什么、改完怎样 | **Action Type**（输入 / **前置条件** / 变更规范 / **副作用** / 权限）· Function · 动态安全 |

核心命题：**传统平台建模"名词"，Ontology 建模"决策"。** Action 是**独立一等类型**，不是实体类上的方法（与 DDD 富血模型有本质区别）。

### 1.2 四大能力判据（视频文案的"扣扳机"）

1. **对象水化** —— 原始数据按本体声明的类/关系落成实例，不是散表。
2. **可推理** —— 沿 Link Type 走图，能答"这个环节缺货会影响谁"。
3. **可执行** —— Action 带前置条件与权限，能写回外部系统。
4. **可审计** —— 每次 Action 留痕，数据可沿血缘下钻。

### 1.3 防幻觉方案（Palantir 侧的三重/四重校验）

| #   | 方案         | 做法                                                                                                 |
| --- | ------------ | ---------------------------------------------------------------------------------------------------- |
| F1  | **数据校验** | LLM 结论必须与 **Ontology 中的结构化数据**比对（**不是**与自由文本比对）                              |
| F2  | **溯源校验** | 结论经权威数据源佐证；每个数字可下钻到底层明细                                                       |
| F3  | **人机回环** | 关键决策 HITL 终审；写回前需授权                                                                     |
| F4  | **置信度过滤** | 抽取带置信度，低于阈值进人工队列，**绝不采信**                                                        |

> **OAG（Ontology-Augmented Generation）关键区分**：Palantir 把**本体对象**注入 LLM 上下文（结构化、确定性）；传统 RAG 把**文本块**喂给 LLM（LLM 需自行解释文本 ⇒ 幻觉空间大）。**「注入对象」与「注入文本」是两种范式，不是同一个方案的两个参数档。**

### 1.4 构建流派（业界通行五派）

| 流派             | 做法                                          | 幻觉风险 | 工程复杂度 |
| ---------------- | --------------------------------------------- | -------- | ---------- |
| 直给派           | 端到端 Prompt 直接出本体                      | **高**   | 低         |
| 框架派           | 预设 Schema，LLM 只做映射填充                 | 低       | 中         |
| 聚类派           | 名词 → 向量 → 聚类 → LLM 命名                 | 低       | 中         |
| 两步走派         | 先出概念清单，再组织层次结构                  | 中       | 中         |
| **拆解派**       | 实体→关系→去重→**双重验证**（结构+逻辑）→存图 | 低       | **高**     |

**Palantir 的实际选择 = 框架派打底 + 拆解派保真 + HITL 人工校验环。** 其本质是「**不让 LLM 创造世界，只让 LLM 理解并映射一个早已存在的业务世界**」。

### 1.5 选型表（三选一的判据）

|              | Palantir Foundry            | Neo4j      | Stardog        |
| ------------ | --------------------------- | ---------- | -------------- |
| 本体类型     | **Operational / Kinetic**   | 属性图     | 语义/虚拟化    |
| 写/动作      | **原生 Action（含 ERP 写回）** | 库内写     | SPARQL Update（受限） |
| AI 集成      | AIP（Logic / OAG）          | Graph RAG  | LLM Connector  |
| 幻觉控制     | **OAG（结构化绑定）**       | 上下文提供 | 逻辑约束       |

### 2.4.1 补充实测（2026-09-15 复核）：门禁有**三块**覆盖缺口，其中一块是「解析能力已具备但零比对」

复核 `check-ontology-consistency.mjs` 第 528-635 行的主流程，`SITES` 循环的 `kind` **只有两个分支**（`:599` 的 `rhai-weight-fallback` 与 `:602` 的 else ⇒ `rhai-band-threshold`）。据此实测三块缺口：

| # | 缺口 | 证据 | 性质 |
| - | ---- | ---- | ---- |
| **G1** | **三力内部权重（`*_PARTS`）零比对** | `parseParts()` 在 `:128` 定义、`:547-549` 被调用于解析权威侧三个 `*_PARTS`，但结果**只用于**三件事：`null` 检查（`:554`）、**权威源自洽**「分项和 = 1」（`:569-573`）、info 打印（`:582-584`）。`:588-635` 的站点循环**没有任何分支**把 `parts` 与副本站点比对 | 🔴 **能力已在、站点未登记**（不是做不到，是没接） |
| **G2** | 同上 ⇒ rhai 里 **16 个内部权重字面量**、分布在 **6 处**，全部在门禁之外 | `bottleneck-calc.rhai:183`（`0.30/0.40/0.30`）、`:192`（`0.60/0.40`）、`:198`（`0.30/0.40/0.30`）；`strategy-scorer.rhai:219`、`:231`、`:235`（同构） | 🟡 隐患（**实测现状数值全对**，见下） | 
| **G3** | `AXIOMS[].enforced_by` 是**自由文本**，无任何门禁 | 断言只有 `!a.enforced_by.is_empty()`（`domain_ontology.rs:841`）；7 条公理填了 7 个测试名（实测**全部真实存在**：`:637 / :660 / :688 / :702 / :730 / :757 / :772`） | 🟡 隐患（现状正确，**改名/删测试不会红**） |

**G2 的现状核验（重要 —— 这不是「现在有 bug」）**：逐处比对本体 `SUPPLY_RIGIDITY_PARTS = [concentration 0.30, barrier 0.40, expansion_cycle 0.30]` / `DEMAND_ELASTICITY_PARTS = [evidence 0.60, certainty 0.40]` / `IRREPLACEABILITY_PARTS = [supplier 0.30, tech_moat 0.40, barrier 0.30]`（`domain_ontology.rs:391-399`）与上述 6 处 rhai 字面量 ⇒ **数值与顺序全部一致，当前无漂移**。

> **⇒ G1/G2 的判据是「覆盖缺口」而非「已存在的数字冲突」**：改任一内部权重，门禁**不会红**，本体会静默腐烂 —— 与顶层权重（有站点守）形成对照。这条正好印证 `MEMORY.md` 的 **#186–#189**（行号引用无门禁会二次腐烂）。
> **⇒ G3 的另一层含义**：7 条公理的 `enforced_by` 指向的**全是本模块自己的单元测试**。即公理守护者**只是测试**，没有任何生产消费者 —— 所以 A4「composite 是加权非等权」这条公理，测的是**常量表里权重不退化**（`domain_ontology.rs:702-726`），**不是** rhai 真的在加权计算（`bottleneck-calc.rhai:200`）。若有人把 `:200` 改成等权平均，**A4 不红、门禁也不红**（门禁只比数字副本，`0.35/0.35/0.30` 原样未动）。这才是 A4 这条公理的真实边界。

### 3.1 为什么 P11 是「范式错」而不是「参数错」

`seed_stock_analysis.rs:1428-1433` 的注释是本次审计**含金量最高的一条自证**：

```
// V74 关闭: hallucination_guard 锚定检查。
// 原因：LLM 输出是分析结论（自然语言），source_context 是工具返回的 JSON 数据，
// 格式天然不匹配导致 2-gram 匹配率极低（实测分数 0.0-0.39，阈值 0.4），
// 几乎所有 AgentNode 都触发 WARN 误报，无实际拦截价值。
// portfolio-mgr.rhai 已有 __untrusted 兜底机制（来自 a-policy 等数据缺失场景），
// 不依赖 hallucination_guard 的输出。
```

**这正是 OAG vs RAG 的分水岭，被项目自己用实测数字证明了：**

- 项目做法 = 拿 **自然语言结论** 去匹配 **JSON 文本** ⇒ 格式天然错配 ⇒ 实测 0.00–0.39 ⇒ 关掉。
- Palantir 做法 = 拿 **结论** 去匹配 **本体对象**（结构化字段、声明过的值域与单位） ⇒ 匹配是**确定的**，不依赖分词。

**⇒ 把阈值从 0.4 调到 0.2 治不了这个病（那是把误报换成漏报）。真正的修法是换锚定面：从"文本锚定"改为"本体对象锚定"。**

## 4. 偏差的性质判定

**不是"本体做得不好"，而是"本体做对了却没接上电"，且防幻觉选错了范式。**

三个层次的问题性质**完全不同**，不可混为一谈：

| 层                     | 性质                    | 通俗说法                                                                 |
| ---------------------- | ----------------------- | ------------------------------------------------------------------------ |
| `domain_ontology.rs`   | 🔴 **做对了但零消费**   | 一份**带测试的规范文档**。它的 11 类 4 关系 7 公理，除测试外无人读       |
| `page_type.rs`         | ✅ **真接线**（反例）    | 载体层的亲和度公理**确实**被 `graph_dtos.rs` 消费 —— 证明这套写法是可行  |
| `hallucination_guard`  | 🔴 **范式错 + 全关**     | 用文本锚定文本；实测误报 ~100% 后被关掉                                 |
| 动态层（Action）       | 🔴 **完全缺席**          | 视频说的"扣扳机"能力，本项目**没有实现**                                 |

### 4.1 一个必须点名的"选位"问题

项目有两个本体，接线状态相反：

```
载体层本体（page_type.rs，页面形态）        → ✅ 真接线，被图谱消费
领域层本体（domain_ontology.rs，瓶颈三力）  → ❌ 零消费，只当常量表用
```

**接电的是"页面类型"这种与投资决策无关的载体词汇；没接电的是"瓶颈/供给刚性/不可替代性"这种正是瓶颈掘金核心的领域词汇。**

这正是 `MEMORY.md` 里那句「`O1` 三段但⚠**选位错**（与 `EdgeType`/`PageType` 零交集 ⇒ 第四套词汇表）」的实证来源。本报告补齐了它的**证据面**：

- 四个并列词汇表，**两两交集为零**：
  - `domain_ontology::CLASSES`（11：Company / Product / Chokepoint / …）
  - `PageType`（14：entity / note / doc / …）
  - `GraphNodeType`（2：entity / note）
  - `ActionKind`（8：Buy / Hold / Wait / …）
- `page_type.rs:18` 自己写着：「把亲和度写进 `domain_ontology` 会造出**第三处**并列词汇表（2026-09-14 已犯过一次）」 —— **说明这个病已被承认识别过，但只防住了"不要再多一处"，没有治"已有四处"**。

### 4.2 与 09-13 二轮审计的关系（不重复、有推进）

二轮审计（Semantica 对比）的结论是「我方在形式化本体维度是 0」，并给出 O1–O4。

**本轮推进**：O1 已落地成 844 行的 `domain_ontology.rs`，**形态上确实不再是 0** —— 有类层级、有 domain/range、有公理、有测试。但本轮实测发现：**它从"0 个本体"变成了"1 个零消费的本体"**，而 Palantir 判据里的**动态层仍是 0**，防幻觉仍是**范式错且全关**。

> ⇒ 建议后续不要再用「本体落地了几条」当进度指标（那是**产出指标**），改用「本体被几个生产消费方读取」+「防幻觉闸门开了几个」（那是**生效指标**）。这正是本项目铁律 11（规则文件 ≠ 检查脚本 ≠ CI 真跑 ≠ 代码真遵守，四链缺一不可）在语义层的同构复现。

## 7. 一句话总结

> **项目的本体不是"没做"，而是"做对了却没接上电"，且防幻觉选错了范式。**
> `domain_ontology.rs` 844 行里，被生产消费的只有 **2 个权重常量 + 1 个渲染函数** —— 11 个类、4 条关系、7 条公理、全部查询能力，**消费方为 0**；声明的 11 个类在所有实例存储里**一个实例都没有**。
> 而 Palantir 判据里真正让 Ontology「能扣扳机」的**动态层（Action Type）完全缺席**；唯一的防幻觉机制（字符串锚定）**在投资决策链的每一个模板里都是 `enabled: false`**（唯一启用的是 OPC 生产模板）—— 而关掉它的那句注释恰好证明了 **OAG 与 RAG 的分水岭**：拿自然语言去匹配 JSON 文本必然失败（实测 0.00–0.39），正确解法是**换锚定面**，不是调阈值。
> 同一仓库里 `page_type.rs`（载体层）**真的接了线**（`graph_dtos.rs:638/640`），说明这套写法可行 —— 问题不在能力，在**选位**：接电的是页面形态，没接电的是瓶颈掘金。
