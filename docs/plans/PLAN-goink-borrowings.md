## 2. 逐条详情

### A1 — 774 行叙事引擎接进工作流 【🔴 P0 · 行为变更】

- **问题**：`harness/src/narrative.rs` 的类型与 API 在模块外**零使用**（AUDIT §2.A）
- **目标状态**：二选一，**必须显式决策**
  - **方案 1（接线）**：`lc-structure-injector` 节点改为「LLM 生成 JSON → 反序列化为 `NarrativeStructure` → 调 `get_chapter_instructions()` 生成每章约束」
    ⇒ 结构指令由**确定性引擎**产出，LLM 只负责「创作初始结构」
  - **方案 2（降级标注）**：若确认暂不接线，在 `narrative.rs` 文件头加 `//! ⚠️ 当前零消费端` 标注 + 在 `PLAN-narrative-structure-enhancement.md` 标记 Phase 1 未完成，**禁止继续以「已实现」计入进度**
- **验证方式**：方案 1 ⇒ `get_chapter_instructions` / `to_prompt_constraints` 的 grep 调用点数由 0 变为 ≥1；
  方案 2 ⇒ 文件头标注存在且计划文档状态更新
- **风险**：⚠️ **这是行为变更**。当前 `lc-structure-injector` 由 LLM 自由生成结构指令（可能「超额完成」）；
  改为引擎驱动后，**结构指令会严格受 `narrative_structure` 约束** ⇒ 输出风格会变。需先跑 1 章对比
- **前置条件**：需产品决策（方案 1 还是 2）

### A2 — 叙事结构落库 【🔴 P0 · 行为变更】

- **问题**：`narrative_structures` 表只由手动 CRUD 写，工作流不读不写（AUDIT §2.B）
- **目标状态**：
  1. `lc-conceive` 输出的 `narrative_structure` 经 `harness::narrative::NarrativeStructure` **反序列化校验**（非法则报错，不静默）
  2. 写入 `narrative_structures`（`is_template=false`，关联本次运行的小说/项目 id）
  3. 下游节点（injector/checker/adapter）**从表读**而非从变量读
- **验证方式**：跑一次文学创作工作流 → `SELECT count(*) FROM narrative_structures` 增 1，且 `structure` 列可被 harness 类型反序列化
- **风险**：⚠️ 行为变更。落库后若校验严格，**之前 LLM 生成的畸形结构会从「静默可用」变成「报错中断」** —— 需先统计历史输出的合法率
- **前置条件**：A1 的方案决策

### A3 — 7 个 KPI 接数据源 【🔴 P0】

- **问题**：`config/opc/industries/content_media/runtime.yaml:64-85` 全为 `constant: 0`
- **目标状态**（按可直算性分档）：

  | KPI | 建议来源 | 可直算性 |
  |---|---|---|
  | `word_count` | 工作流产出章节的字数统计（goink 用 `writing_log.word_delta`） | ✅ 可直算 |
  | `completion_rate` | 已完成章数 / 大纲章数 | ✅ 可直算 |
  | `revision_rounds` | 反逻辑校验 + 结构校验节点的实际触发轮次 | ✅ 可直算 |
  | `content_count` | 已产出作品数 | ✅ 可直算 |
  | `page_views` / `conversion_rate` / `content_engagement` | **无数据源** ⇒ 建议**删除**而非留 `constant: 0` | ❌ 应删 |

- **验证方式**：跑完工作流后 KPI 面板非 0；`runtime.yaml` 中不再存在 `type: constant` 的 KPI
- **风险**：低。但**删 KPI 会改变面板布局**（`dashboard_cards` 引用 `kpi_key`，需同步）
- **前置条件**：确认「留 0 等数据源」vs「删掉」的产品决定

### A4 — 修 `current_chapter` 悬空路径 【🔴 P0 · 行为变更】

- **问题**：`seed_content_media.rs:1097,1141` 引用 `lc-chapter-structure.current_chapter`，**全仓零产出点**（AUDIT §2.D）
- **目标状态**：Loop 节点的 `iteratee_var: "chapter"` 已把当前章注入 scope ⇒ 应改为**按当前章号索引**，例如
  - 若引擎支持动态键 ⇒ `lc-chapter-structure.{chapter.num}` 或等效语法
  - 若引擎不支持 ⇒ **新增确定性节点/内建变量**把「当前章的结构指令」提升为独立变量（比照 goink 的 `builtin_vars`）
- **验证方式**：
  1. `grep -rn "current_chapter"` 结果为空（或仅剩有产出点的合法引用）
  2. **实测**：跑 1 章并 dump `lc-draft-chapter` 的最终 system_prompt，确认约束段**非空**
- **风险**：⚠️ **这是行为变更，且是「从失效变生效」**。当前该输入恒空 + prompt 兜底「若约束为空，可自由推进剧情」⇒
  **修完后创作行为会明显变化**（出现强制结构约束）。**必须先在单章上对比**，不可直接全量跑 50 章
- **前置条件**：无（可直接开工）

- **验证方式**：`grep -rn "NarrativeKpiMetrics"` 命中 ≥2（定义 + 消费）

### B5 — 写完自动注入维护提醒 【🟠 P1 · 核心借鉴】

- **问题**：我方结构校验是**编排层节点**（`lc-structure-checker` 排在创作之后）—— 若节点被删/工作流被绕过就没了
- **借鉴来源**：goink `internal/mcp_tools/rw_tools.go:228-237`
  —— **在「写正文」工具的返回值里注入检查清单**。工具返回是每轮必读内容 ⇒ 提醒必然出现在上下文
- **目标状态**：在写正文的节点/工具产出中**固定追加**维护清单（伏笔状态 / 弧线推进 / 角色变化 / 读者认知 / 章节计划），
  与「编排层校验节点」形成**双层保障**（编排层管流程、产出层管强制）
- **验证方式**：dump 写正文节点的输出，确认尾段含检查清单；**并统计清单项被真实响应的比例**
- **风险**：低。但**清单会占 token**，需评估长度
- **注意**：goink 的做法是「提示 LLM 自己调工具写状态」；我方若走**确定性落库**（A2），
  则此清单应改为「LLM 需判定的部分」，**不要把可确定性计算的东西交给 LLM 自评**

### B6 — 「自由文本 vs 枚举」判据 【🟡 P2】

- **借鉴来源**：goink 的类型注释记录了明确的判据 ——
  `internal/location/types.go:12-19`「系统不需要根据 `location_type` 执行不同行为……纯标签 ⇒ 自由文本」；
  `internal/storyarc/types.go`「`arc_type` 驱动过滤和注入策略 ⇒ 保持约束枚举」；
  `internal/timeline/types.go`「`category` 驱动不同的查询和注入策略 ⇒ 需精确行为区分」
- **落地判据**（建议写入 `AGENTS.md` 或判据层）：
  > **字段是否驱动系统行为？** 驱动 ⇒ 约束枚举（穷举分支）；
  > 仅作标签/过滤/展示 ⇒ 自由文本。**不要把「AI 该填什么」当成枚举设计的依据。**
- **验证方式**：对现有 DTO 做一轮扫描，找出「枚举但无任何分支消费」的字段（应为自由文本）与
  「自由文本但被字符串比较驱动」的字段（应为枚举）
- **风险**：低（文档级）

### B9 — 写作方法论 87 条 → 评审节点判据 【🔴 P0 · 性价比最高】

- **借鉴来源**：goink `internal/skill/builtin/` 12 个技能 md，提炼 87 条（全文见 `recon-D-style-pattern.md` §4）
- **为什么性价比最高**：**这些是可量化的判据，能直接替换我方现在空泛的「请检查节奏是否合理」**
- **可直接变成硬判据的示例**（我方当前 prompt 无任何量化）：

  | 维度 | 可量化判据（goink 提炼） | 我方现状 |
  |---|---|---|
  | 去 AI 味 | 10 项扣分清单（排比总结句 / 情感直白标注 / 句长匀速 / 定节奏标记词 / 过度因果连接 / 形容词叠加 / 人物全知化 / 对话标签膨胀 / 强制正能量收尾 / 「众所周知」变体） | 无 |
  | 对白潜台词 | **潜台词密度 ≥50%** | 无 |
  | 节奏 | 连续 3 页同一节奏即报警；快慢段落间需插入缓冲 | prompt 只写「叙事节奏是否合理」 |
  | 场景 | **至少 3 个 Try-Fail Cycle**；每个场景至少完成两件事 | 无 |
  | 伏笔 | **每个重要伏笔至少出现两次**；回收后必须留涟漪 | 无 |
  | 修改 | **二稿 = 一稿 − 10% 字数**；永远从大到小改 | 无 |

- **目标状态**：
  1. 把上述判据写进 `lc-structure-checker` / `lc-anti-logic` 的 prompt（**自撰措辞**，AGPL 边界）
  2. 输出 schema 增加**可核对字段**（如 `ai_flavor_hits: []`、`subtext_ratio: 0.5`），而非只有 `compliance_score`
  3. 让 LLM **逐项打分**而不是给一个主观总分
- **验证方式**：`compliance_score` 与逐项命中数的相关性（当前是无锚定的主观分）；
  并做**小样本 A/B**：同一章分别用旧/新 prompt 生成，人工盲评
- **风险**：低（prompt 层）。但**必须实测效果**，不可假定「抄了规则就变好」（AUDIT §7.7）

### B11 — prompt 分层（KV cache）【🟠 P1】

### C1 — 「统计先行、LLM 后归纳」【🔴 P0 · 零成本】

- **借鉴来源**：goink `internal/style/extract.go` —— **先用代码统计出确定性特征（长度分布 / 方差 / 密度），
  作为结构化文本塞进 prompt，并明确告诉模型「这些数值是代码算的，直接引用」**，然后才让 LLM 归纳
- **目标状态**：凡「从文本/数据反抽规则」的节点一律先算统计量。可用于：
  - 文风分析（句长分布 / 词汇丰富度 / 标点密度）
  - 章节质量体检（字数 / 段落数 / 对白占比）
  - **A3 的 KPI 计算**（`word_count` 等本就该由代码算，而不是问 LLM）
- **验证方式**：节点 prompt 中出现「以下数值由代码统计得出，请直接引用」类声明；LLM 输出不再包含自算数字
- **风险**：无（纯增强）

## 3. 明确不做（防范围蔓延）

| 不做 | 理由 |
|---|---|
| **不移植 goink 的代码 / prompt 原文** | AGPL-3.0 传染性；87 条方法论须自撰措辞 |
| **不引入 SQLite + GORM** | 我方是 sea-orm + PG/SQLite，栈不同 |
| **不引入内置 git 作为正文版本控制** | 用户 git 零接触铁律；且 goink 这条路径本身回滚入口缺失（⛔D4） |
| **不引入 ONNX 本地嵌入（B15 暂缓）** | 我方已有本地 embedding 服务（localhost:8091 / bge-m3 1024 维）；**先接现有服务，不另起一套** |
| **不改为对话式 ReAct 架构** | 我方节点图编排是更强的工程资产（AUDIT §5.2）；只在**状态维护**层借鉴其纪律 |
| **不抄其审批/回滚/技能安全实现** | 三者均为 fail-open（⛔D1-D3） |
| **不为其「关系无需结构化边表」的设计辩护** | 我方 `NarrativeStructure` 有交汇点概念，强于其弧线节点链；**不在弱项上做伪对冲** |
