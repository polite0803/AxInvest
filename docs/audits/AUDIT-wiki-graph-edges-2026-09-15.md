## 0. 结论（三句话）

1. **不是数据问题。** 库里有 **74791 条边**、24288 个节点中**只有 2 个是孤立点**，社区也已算好。后端下发的是完整图。
2. **边是被前端渲染层自己丢掉的** —— 三重叠加：节点按哈希降采样 50% 后**被当作边端点过滤器**（边保活率 ≈ 0.25）、边再降采样 30%、线宽是**世界坐标里被二次缩放**的 `0.45·zoom² px`（zoom≤0.5 时恒 < 0.11px）叠加 20% alpha。
3. **分组是结构性没有** —— 社区气泡层的门槛是 `communities.size <= 800`，而实测 `communities.size == 24288` ⇒ 气泡层与聚类标记层**在本数据集上永久为死代码**。

WeKnora 与我们的根本差异**不在渲染技巧**，而在**谁负责裁剪**：它**在服务端**按「度数 Top-500 / ego BFS」切一个**连通的子图**下发；我们**全量下发 24288 节点 / 12.8MB**，再在前端用**哈希随机采样**去砍。

> **修复状态（2026-09-15，当日闭环）**：R1 / R2 / R3 / R4 / R5 **已全部修复并验证**（改动清单与实测数字见 §4.2–§4.5）。
> F4（服务端切片）**未实施**（理由见 §4.6）；F5（陈旧缓存）**已定位未修**（结论见 §4.7，修法待你选修）。

> **⚠ 第 3 句需要补一句（§6 量化后）**：气泡层的**判据**已修（F3，`communities.size` → 不同社区 id 数，实测已执行），
> 但**分组仍然看不见** —— 因为**分桶本身是随机的**（R6，§6.4：同区内边 0.49% ≈ 随机期望 0.50%），
> 且它是「一片均匀分布的点」这一宏观形态的直接成因（聚合图边密度 82.69%）。
> 像素级结论：相邻节点同色率提升仅 **1.010×**（§6.3）。**分组的缺失是语义问题，不是阈值问题。**

## 2. 根因链（每条都带代码锚点）

### R1 — 节点降采样集合被当作**边端点过滤器**（边保活率 ≈ 25%）

`GraphView.tsx:2482`：

```ts
const nodeSampleRate = isLargeGraph ? 0.5 : 1.0;   // isLargeGraph = nodes.length > 5000 (:1842)
```

`:2485-2490` 按 **node id 哈希**确定性丢掉 50% 节点，得到 `visibleNodes`；随后 `:2546` 用**这个被采样后的集合**建 `idSet`，`:2576`：

```ts
if (!idSet.has(em.source) || !idSet.has(em.target)) { continue; }
```

⇒ 一条边要被画出来，**两端都必须各自命中 50% 采样**，概率 `0.5 × 0.5 = 0.25`。

**这是核心缺陷**：为了性能对节点做子采样是对的，但把它同时当成边的可见性判据，会让「点数」和「边数」以**平方关系**脱钩 —— 屏幕上剩下的一半点里，只有约 1/4 的边还连着，视觉上自然「一片无关系的点」。

### R2 — 边自身再降采样 30%（与 R1 相乘 ⇒ 7.5%）

`GraphView.tsx:2556-2561`：

```ts
if (isLargeGraph) {
  edgeSampleRate = zoom < 0.3 ? 0.15 : zoom < 0.5 ? 0.3 : 0.5;
}
```

配合 `autoFit` 后的 zoom（见 R3）通常落在 `zoom < 0.5` 档 ⇒ `0.3`。
`0.25 × 0.3 = 7.5%` ⇒ 74791 条边只剩约 **5600 条**参与绘制。

### R3 — 线宽在世界坐标里被**二次缩放**（`∝ zoom²`，恒亚像素）

渲染循环 `:1282-1283` 把整个场景放进相机变换：

```ts
ctx.translate(w / 2 + cam.x, h / 2 + cam.y);
ctx.scale(cam.zoom, cam.zoom);
```

所以 `ctx.lineWidth` 是**世界坐标**单位，落到屏幕要再乘一次 `zoom`。而 `:2566-2568`（`drawExpandedCommunity`）与 `:2678-2680`（`drawEdgesOptimized`，同一公式，重复两份）写的是：

```ts
const baseWidth = 0.3;
const zoomScale = zoom < 0.5 ? zoom * 1.5 : Math.min(1, zoom);
const dynamicWidth = baseWidth * zoomScale;
```

⇒ 屏幕线宽 = `0.3 × (1.5·zoom) × zoom = 0.45·zoom²`

| zoom | 屏幕线宽 | 叠加 alpha | 有效覆盖率 |
|---|---|---|---|
| 0.05（`handleZoomOut` 下限，`:4148`） | **0.0011 px** | 0.12 | 0.01% |
| 0.15（R4 的硬丢弃阈值） | 0.0101 px | 0.12 | 0.12% |
| 0.27（`handleFitAll` 典型初值） | **0.0328 px** | 0.20 | **0.66%** |
| 1.0（100% 缩放） | 0.30 px | 0.35 | 10.5% |

**「屏幕恒定 N 像素」的正确写法是 `N / zoom`；代码写成了 `N × f(zoom)`，方向反了** —— 于是**越缩小线越细**，恰好与「缩小时需要更粗才看得见」的意图相反。公式括号里的 `zoom * 1.5`（`zoom < 0.5` 分支）说明作者**意图**是补偿，但补偿写在了会被变换再乘一次的量上。

> 补充：`handleFitAll`（`:4185-4189`）`targetZoom = min(w·0.8/bboxW, h·0.8/bboxH, 2)`；初始布局半径 `graphPhysics.ts:524` `radius = max(minDim·0.5, √n·8)` ⇒ 24288 节点得 `radius ≈ 1247`（世界直径 ≈ 2494），配合 ~1200×800 视口 ⇒ 初值 zoom ≈ **0.27**。
> **关键**：`zoom ≤ 0.5` 时屏幕线宽恒 `≤ 0.11 px`，所以**无论精确 zoom 是多少，结论都成立** —— 该区间内边必然亚像素。

### R4 — `zoom < 0.15` 时**硬丢弃全部非交互边**（另一条独立路径）

`drawEdgesOptimized:2723`：

```ts
if (zoom < 0.15 && !isRelevant) { continue; }
```

这不是淡出，是**整段跳过**。而 `handleZoomOut:4148` 允许用户一路缩到 `0.05` ⇒ 用户手动缩小后，`drawEdgesOptimized` 路径下**一条边都不会画**。`drawExpandedCommunity` 没有这条硬跳过，但 R3 会让它同样不可见。

### R5 — 分组：气泡层与聚类标记层在本数据集上**永久不可达**

三条独立的门同时关死：

| 层 | 代码位置 | 门槛 | 实测 | 结果 |
|---|---|---|---|---|
| 社区气泡 | `:1780-1787` | `clusterModeRef && communities.size <= MAX_AGG_PHYS_NODES` | `communities.size = 24288`（条目数）> 800 | ❌ 不画 |
| 聚类标记 | `:1928-1935`（在 `allCollapsed` 分支内） | `collapsedRef.current.has(cid)` | 自动模式下 `collapsedRef` 被**刻意清空**（`:1122`） | ❌ 不画 |
| 节点色 | `buildNodeColorCache` | 类型映射 | 可画，但被 R1 采样掉一半 | 只剩散点 |

`MAX_AGG_PHYS_NODES = 800`（`:441`）的语义是**「聚合物理规模上限」**，却被同时用作**「社区数上限」**（`:1782`）。而本数据有 **2458 个真实社区**，必然超限 ⇒ 气泡层死。

更狠的是 `:1782` 判的是 `communities.size`（=**24288 个 Map 条目**）而不是**不同社区 id 的个数**（2458）。即便把阈值调到 3000，判据仍然是错的量 —— **这是「判据量取错」而非「阈值设小」**。

> 附：`effectiveCommunitiesRef` 已在 `:909` 做哈希合并（>800 社区时并到 `FORCE_CLUSTER_COUNT = 200`），所以聚合物理侧有 200 个虚拟桶可用 —— 但气泡层读的是**原始 prop**，两者不衔接。

**⇒ 「既没有分组，也没有关系，全是一片无关系的点」= R1+R2+R3 让边消失，R5 让分组消失。**

### 3.2 值得直接借鉴的三条（按性价比排序）

1. **服务端 overview/ego 切片 + `Meta.total`**（最高价值）
   把 `get_wiki_graph_cached` 加 `mode` / `center` / `depth` / `types` / `limit` 参数；overview 按度数取 Top-N（N 可以比 500 大得多，比如 2000，因为我们是 Canvas 不是 SVG）；`Meta` 回报 `total`，让工具栏的 `24288N / 74791E` 变成 `2000 / 24288 节点（显示中）`。
   ⇒ **一举解决 R1/R2/R3 全部**（节点少到不需要采样，也就没有平方衰减；边宽公式修正后能正常看见）。

2. **`preserveLayout` 增量扩邻（bloom）**
   WeKnora 的 `RenderGraphOpts{preserveLayout, anchorSlug}`（`WikiBrowser.vue:3752-3757`）是新节点落位复用旧坐标、只在锚点附近抖动 —— 我们重载图时会整片重排。这条不需要改后端，收益明显。

3. **线宽归一：`N / zoom`**（纯 bug 修复，零架构成本）
   R3 是**算错**不是设计选择，两处公式（`:2566-2568`、`:2678-2680`）应统一为一个 helper，并用「屏幕恒定 1px」反推。顺带删掉 `:2723` 的 `zoom < 0.15` 硬丢弃。

### 3.3 不建议借鉴

- WeKnora 的**实体知识图谱**（Neo4j 路径）—— 默认关闭，`query_knowledge_graph` 的 `edges` 初始化后从不填充（前次审计已记为 ⛔ 8），是「有 UI 没数据」的典型。
- 它的 **SVG 渲染**：500 节点以上会退化（注释自陈「100k SVG nodes」是它要防的东西）。我们保留 Canvas。

### 4.3 判据选择说明（F3 为何用「虚拟桶」而不是「真实社区」）

`effectiveCommunitiesRef` 在大图（>3000 节点）下会把 24288 个节点的社区映射**哈希合并到 200 个虚拟桶**
（`:906-948`，`FORCE_CLUSTER_COUNT = 200`），并且这个合并后的映射**同时喂给物理 Worker**
（`nodeIdxToCommunity`，`:1047-1052`）—— 即 Worker 的社区力按这 200 个桶把同桶节点拉到一起。

因此气泡**必须**按同一套桶来画，否则「气泡包围盒」与「节点实际聚集位置」不一致，会画出一堆互相重叠的大椭圆。

> **⚠ 更正（2026-09-15 §6 量化后回改）**：本节原先写「随机桶替代真实社区**不是**本次『看不见分组』的成因」——
> **这句是错的**。§6.4 实测：该分区的同区内边占比 **0.49%**，与其随机期望 **0.50%** 相等；
> §6.3 的像素判据给出相邻节点同色率提升仅 **1.010×**。
> 即：**「看不见分组」的成因正是这套随机桶**，且它还是「24288 个点均匀铺满一盘」这一宏观形态的直接成因
> （随机分桶使聚合图边密度达 **82.69%**，逼近完全图 ⇒ 力导向退化为均匀铺开）。
> 本节其余部分（气泡必须与物理同源）仍然成立。

真实 Louvain 社区（2458 个）在本数据集上**没有进入渲染** —— 属**语义降级**，
且经 §6 证实它就是「没有分组」的根因，已升级为 §6.5 的 **F6**（前半段为纯缺陷）。

## 6. 气泡密度 / 分组可见性的像素量化（2026-09-15 补做）

### 6.0 三句话结论

1. **气泡层在屏上没有可分辨的边界**：以「大面积染色块」为判据，整块画布是**一个**连通域，
   覆盖 **99.97%**（阈值扫描：t≥6 → 99.97%，t≥8 → 99.75%，t≥12 → 71.53%）⇒ 不存在「一个个气泡」这种结构。
2. **分组在视觉上与随机分配不可区分**：相邻节点的「同色相」率 **11.14%**，
   随机分配的期望值 **11.04%** ⇒ 提升仅 **1.010×**。
3. 原因不是气泡层的判据（§4.2 的 F3 已修好、且实测确认已执行），而是
   **R6：200 个哈希桶的分桶本身就是拓扑无关的随机划分**，并且**无条件执行**（真实 Louvain 结果被整体丢弃）。
   - **量化补证**：现行哈希划分的 **modularity Q = −0.0005** ⇒ 与随机划分**无统计区别**（Q 减去随机期望项，随机划分恒为 0）。
   - **已修**（2026-09-16）：分桶换成**拓扑感知归并** ⇒ Q **0.6607**、同区内边 0.49% → **68.35%**（§6.8）。
   - **像素级复测已跑通**（2026-09-16 01:40）⇒ 结论见 **§6.10**：
     四条像素判据**全部未达成**，但**根因与此处的 R6 无关** —— 气泡确实被绘制，问题在
     **每个气泡的半径 ≈ 0.78~0.86 倍画布对角线**，200 个必然完全重叠 ⇒ 视觉上是一片均匀染色。
     这是一条**与分桶策略无关**的既有缺陷（`aggActive=false` ⇒ 社区未被力导向分离 ⇒
     `drawClusterRegions` 按包围盒定半径必然退化成全屏糊）。

### 6.1 harness 前置：主画布首屏空白（**R7，本次新发现**）

**现象**：headless 打开 `/llm-wiki/<vault>/graph` 后，主画布**连续 240 秒零高亮像素**，
`[GraphView] render path` 诊断日志**一条都没有**（该日志每 60 帧一条，本该每秒约 1 条）。

**机制（三段闭合）**：

| 段 | 代码锚点 | 事实 |
|---|---|---|
| ① 大图 Worker 未就绪 ⇒ 走 fallback 分支 | `:1713` | Worker 未 ready 时进入主线程 fallback |
| ② fallback 里 `stable` **恒为 true** | `:1717-1720` | `mainThreadSafe = nodes.length <= 1500` ⇒ 24288 节点时为 false ⇒ `stable = true` ⇒ `idleCounterRef` **每帧 +1** |
| ③ 约 1 秒后**永久早退** | `:1262-1268` | `idleCounterRef > 60` 且鼠标不在画布内 ⇒ `requestAnimationFrame(render); return;` —— 位置在**画布绘制之前**，且**没有任何东西复位它** |

Worker 随后 ready（实测打出 `refreshClusterGeom success {bucketCount: 200}`）、
`workerInitializedRef = true`，但循环已经冻在 ③ ⇒ **主画布保持空白**。

**影响面**：这不是「渲染慢」，而是**用户不把鼠标移进画布就永远看不到图**。
鼠标进入画布（`mouseScreenRef.active = true`）即解冻 —— 用户报告能看到「一片点」，
说明他们动过鼠标，所以这个缺陷在他们那边表现为「先空白、动一下才出来」，而非永久空白。

**对本次量化的影响（重要）**：第一版 harness 没模拟鼠标存在，量到的是一张**只有背景渐变的画布**
（blob 数 0、强对比像素占比 0.00%）。**若不做这层排查，本报告会给出「气泡密度为零」的假结论。**
修正后（鼠标停在画布顶边、不落在节点上，避免触发 hover 降级渲染）才拿到 §6.3 的真实数据。

### 6.2 判据三次试错（方法论留痕）

| 版本 | 判据 | 结果 | 为什么错 |
|---|---|---|---|
| v0 | 距离变换「厚块」（distance ≥ 3） | 844 块，中位面积 **4px** | 量到的是**节点精灵**（2~3px 实心圆）；气泡是 alpha 0.12 的淡渐变，永远进不了高对比掩膜 ⇒ **量错对象** |

### 6.4 R6：「200 个虚拟桶」的来源与量纲错

**它是怎么来的**：`FORCE_CLUSTER_COUNT = 200`（`GraphView.tsx:443`）**来自 upstream** ——
`.worktrees/upstream/src/components/wiki/GraphView.tsx:356` 有逐字相同的定义与注释。
即：不是本项目为这份数据算出来的数，是从上游继承的魔数。

**注释与代码说的不是一回事**：

| 位置 | 内容 |
|---|---|
| `:442` 注释 | 「强制聚类数量上限：**当社区数超过此值时**，通过哈希合并到虚拟聚类」⇒ 本意是**阈值**（社区数 > 200 才合并） |
| `:925` 代码 | `effectiveCommunities.size > MAX_AGG_PHYS_NODES`，而 `effectiveCommunities = Map<nodeId, cid>` ⇒ `.size` 是**节点条目数**，不是社区数 |

**恒真证明**：该分支仅在 `shouldForceCluster = pNodes.length > 3000`（`:923`）时进入；
此时若 `communities` 覆盖全部节点，则 `size = 节点数 > 3000 > 800` ⇒ **条件恒为 true**
⇒ 哈希合并**无条件执行**。「社区数 > 200 才合并」被实现成「节点数 > 800 就并到 200 桶」——**三个量被混成一个**。

> 本数据集 `communities` 恰好覆盖全部 24288 个节点（实测 `communities entries=24288`），
> 所以本条对**当前数据必然成立**；对小图（3000~800 节点区间）不成立但也不进入该分支。

**后果量化**（用本机 PG 真实 74791 条边逐边跑，脚本见 §6.6）：

| 分区 | 小区数 | 最大小区 | 同区内边占比 | 均匀随机期望 | 聚合图边密度 |
|---|---|---|---|---|---|
| **(a) 哈希 200 桶（现行）** | 200 | 153 | **0.49%** | 0.50% | **82.69%**（16456/19900） |
| (b) 真实 Louvain | 2458 | 214 | **57.84%** | 0.09% | 0.46% |
| (c) 真实社区 top-199 + 尾社区归并 | 200 | 18471 | **65.81%** | — | **8.09%**（1609 条） |

**(a) 的同区内边占比 0.49% 与其随机期望 0.50% 几乎相等** ⇒ 现行分组在拓扑上**就是随机划分**；
这一步与 §6.3 的像素级结论（1.010×）互为**独立佐证**（一个走拓扑、一个走像素）。

**聚合图边密度 82.69% 是宏观形态的直接成因**：力导向看到的只有「200 个聚合节点 + 去重后的聚合边」，

**(c) 把聚合边从 16456 条降到 1609 条（8.09%）** —— 结构才有显现的余地。

### 6.8.1 ⚠ 为什么 F6 必须与 `:1808` 一起改

`GraphView.tsx:1805-1808` 的气泡层开关是：

```ts
const clusterCount = communityCentroidsRef.current.size;   // = 不同桶 id 的个数
if (clusterModeRef.current && clusterCount > 0
    && clusterCount <= MAX_AGG_PHYS_NODES                  // 800
```

现在它能通过，是因为 `:925` 的归并分支把桶数压到 **200 ≤ 800** ——
**这是巧合，不是设计**。若按直觉把分桶换成真实 2458 个社区，`2458 > 800` ⇒ 判据为假 ⇒
**气泡层再次消失**（这正是 F3 修好前的老症状，会以「修了 F6 反而更糟」的形态回来）。

⇒ 两处必须拆开：

| 位置 | 该比的量 | 常量语义 |
|---|---|---|
| `:925` | **不同社区 id 的个数** | 「归并触发阈值」（社区数上限） |
| `:1808` | **聚合节点数**（= 桶数） | 「气泡/聚合物理规模上限」（`MAX_AGG_PHYS_NODES`） |

并保证 `:925` 的归并结果 **≤** `:1808` 的阈值。

### 6.8.2 判据的三次修正（方法论留痕 —— **两次错的都是判据，不是数据**）

| 版本 | 判据 | 它得出的结论 | 为什么被否 |
|---|---|---|---|
| v1 | **同区内边占比** | —— | 把大量小社区塞进同一个桶，会让「桶内边」**人为变多** ⇒ 该值虚高。实测 (c)「尾部全归 other」得 **64.18%**，反而**高于**真实社区的 57.84% ⇒ 数值更高、语义更差（它的桶里装着 **71.30%** 的节点，N=300 时最大桶 17317 个节点） |
| v2 | `cohesion = Σ(桶内实际边数) / Σ C(桶大小,2)` | N=300 优于 N=200；且 **Huffman（按规模合并）4.17% 优于拓扑归并 1.12%** | **它同样被桶大小分布主导**，只是方向相反：拓扑归并的桶呈**幂律**（存在 900~922 的巨桶）⇒ 分母被抬到 C(922,2)≈42 万 ⇒ 该值被**压低**；而 Huffman 的桶大小**均衡** ⇒ 分母小 ⇒ 该值被抬高。于是这个判据实际在奖励「桶大小均衡」而非「拓扑正确」—— 而 Huffman 的 Q 只有 **0.5740**，明显更差 |
| **v3（采用）** | **modularity Q** + **NMI(vs 真实社区)** | N=200 在 Q / 聚合边 / 气泡三项占优 | — |

**通用教训**：占比型判据必须先问一句 ——「**有没有一个自由度能让它变好、而实际上变差？**」

| 判据 | 它的自由度 | 后果 |
|---|---|---|
| 同区内边占比 | 桶数、桶大小 | 把桶做大 ⇒ 虚高 |
| `cohesion` | 桶大小**分布** | 把桶做匀 ⇒ 虚高 |
| **Q（modularity）** | —— | 它**减掉了随机期望项**，随机划分恒为 0 ⇒ 无法靠「做桶」刷高 |

Q 与 NMI 的取值口径（本报告所有表格同此）：

```
Q   = Σ_c [ L_c / m − (d_c / 2m)² ]     L_c=桶内边数, d_c=桶内节点度数和, m=有效边数
NMI = I(X;Y) / [(H(X)+H(Y))/2]          X=策略划分, Y=真实社区
```

Q ≈ 0 即「与随机划分无区别」—— 这正是现行哈希分桶的实测值（**−0.0005**）。

> ⚠ `cohesion` 并非无用：作为**气泡可读性的代理**它仍有解释力（气泡半径取桶内节点
> 包围盒/2 + 40，`:2255-2256`；桶内节点越拓扑抱团 ⇒ 包围盒越小 ⇒ 气泡越紧凑）。
> 但它**不能用来跨策略比较**，本报告仅将其列作参考列。

**#1 的关键优化 —— 为什么必须「一轮并行合并多对」**（这是耗时从 1.24s → 46ms 的全部原因）：

朴素版每轮只为整个图选**一对**最优合并（经典 Louvain 第一阶段），于是需要
`社区数 − N` = 2458 − 200 = **2258 轮**，且每轮的邻接表扫描范围随合并**持续增长** ⇒
总成本被轮次数放大。四版实测梯队：

| 版本 | N=300 实测 | 相对 |
|---|---|---|
| 朴素（每轮一对） | 1242ms | 1× |
| 缓存「最佳伙伴」（避免每轮全扫） | 883ms | 1.4× |
| **惰性最大堆**（教科书优化） | **1291ms** | **0.96×（更慢！）** |
| **一轮内并行合并多对**（采用） | **46ms** | **27×** |

> 惰性最大堆**变慢**是本次的意外发现：堆的维护成本（每次合并要更新邻居的 gain）
> 超过了它省下的比较次数，且它仍未减少**轮数**。而并行匹配把轮数从 2258 降到 **20 轮**，
> 同时**质量更高**（Q 0.6592 vs 朴素 0.6592 持平、聚合边更低），因为没有「每轮只挑全局最优」
> 造成的顺序依赖。⇒ **优化前先问「成本被什么放大了」——这里是轮数，不是比较次数。**

**#3 的实现要点（两个必须做对的地方）**：

1. **并查集解析**：合并只记录「谁并进谁」（`parent[b] = a`），最终「节点 → 桶」必须
   **沿链解析**（带路径压缩）才能拿到桶。**漏掉这一步会静默丢节点** —— 这是单测抓到的实现 bug，
   也是三个早期分析脚本的共同缺陷（§6.8.3 的 ⚠）。
2. **兜底路径不产生新 id**：社区图零有效边时退化为「按已有桶 id 集合做哈希」，桶内仍是
   **已存在的簇**，不依赖真实 cid 的数值范围（§6.7 指出：依赖 cid 值域是危险写法）。

   背景渐变属于**细像素**（基线实测 `thin(d≤2)=90709px` 占 94.97%）⇒ 不会污染质心集。
2. `analyze-node-hue` 是 §6.2 试错三次后采用的 **v2 判据**，判据层级落在「节点」而非「像素」。

   这一点在 §6.2 的 v1 试错里已经吃过一次教训（当时「众数背景色差分」判据就是这么失效的）。
4. 因此：**若四者结论矛盾，以 1 和 2 为准。**

> ⚠ **上面这个「可靠性排序」已在 §6.10.2 被推翻两处，保留原文仅作留痕**：
> - 第 1 条（`analyze-blobs` 最干净）**只对「节点级」成立**。它只对 `diff ≥ 24` 的**强**像素做连通域，
>   而气泡中心 alpha 仅 **0.12** ⇒ 气泡**必然落在 faint 带** ⇒ 它对**气泡层**是**结构性不可能检出**的。

>   而是**失效**（`f6b` 上 `t=2` 就 100% 覆盖）⇒ 它的 99.3% 是**假阳性**，不能读作「一个大气泡盖住全屏」。

> （半径 / 画布对角线）；`analyze-blobs` / `analyze-node-hue` 只用于判「**节点**的位置与颜色是否有分组结构」。

**关于「渲染路径断言」为什么必须加**：`shouldUseClusterRender = (aggActive || clusterModeRef.current || forceCluster) && geomReady`
（`GraphView.tsx:1859-1860`，`geomReady = clusterGeomRef.current.size > 0`）。它为假时走的是**原始渲染路径**
—— 直接画 24288 个节点、**根本不画气泡层**。而同一份 F6 构建的两次运行给出了**视觉形态完全不同**的结果

否则判据可能在量一个根本不含被测对象的画面。断言手段见 §6.10.3。

### 6.10 渲染期判据实测与根因定位（**新章节，2026-09-16 01:40 定案**）

本节回答上一轮遗留的唯一问题：**渲染期的四条判据为什么全都没动**。

#### 6.10.1 根因：一条每一环都有证据的因果链

**结论先行：气泡被画了，但每个气泡的半径约等于画布对角线 ⇒ 200 个必然完全重叠 ⇒ 视觉上是一片均匀染色。**
这条链**与分桶策略无关**，因此「哈希 → 拓扑归并」不可能改善渲染期判据。

| # | 链路 | 证据（可复跑） |
|---|---|---|
| ① | 大图（24288 > `AUTO_CLUSTER_THRESHOLD` 3000）⇒ `shouldForceCluster` ⇒ 设 `isAutoForceClusterRef = true` 且 `collapsedRef.current = new Set()`（`:1171-1173`，注释明写「默认不折叠社区，让用户看到真实节点」） | 基线诊断日志 `renderpath-args.json`：`autoForce: true, collapsedSize: 0` |
| ② | `collapsed.size === 0` ⇒ `buildAggregatePhysics()` 在 `:3278` **硬早退**（`aggPhysRef.current = null`）⇒ **聚合物理永不激活** | 同上日志：`aggActive: false` |
| ③ | ⇒ 力导向跑的是 **24288 个原始节点**（不是 200 个聚合节点）⇒ 各社区成员**散布全图**，在**坐标空间里没有被分离** | `analyze-blobs`：最近邻质心距离 / 泊松期望 = **1.058**（≈1 即与随机撒点不可区分） |
| ④ | `drawClusterRegions` 用 `rx = (maxX − minX)/2 + 40`（`:2289-2290`）**按包围盒**定气泡半径 ⇒ 每个社区的 bbox ≈ 整张画布 | 本探针实测 **半径 / 画布对角线 = p50 0.778、max 0.922**（另一次运行 0.855 / 1.012）；`gradR1` 与 `ellipseRadii` 的 p50 只差 1px，互为印证 |
| ⑤ | ⇒ 200 个半径 ≈ 半屏对角线的极淡（alpha 中心仅 **0.12**，`:2293-2295`）椭圆**完全互相重叠** ⇒ 视觉产物是一片均匀染色 | `probe-bubble-A-on.png`（整屏青蓝雾）vs `probe-bubble-B-off.png`（主画布全空）；该雾**不是**背景 —— 背景是 `colorBgContainer → colorBgElevated` 的主题灰径向渐变（`:1275`） |

**为什么「无变化」才是正确预期**：改动 A（分桶策略）若与判据不在同一条数据通路上，判据就会**纹丝不动**
—— 不是因为 A 没用，而是因为判据根本不在 A 的下游。**分区算法**决定「拓扑正确性」，**布局的单位**（聚合节点 vs 原始节点）
决定「空间聚集」，这是两条独立通路。改动 A 只能改善前者（Q **−0.0005 → 0.6607**，同区内边 **0.49% → 68.35%**），
而四条像素判据量的是后者。

1. **前提未断言**（最严重，已修）—— 见 §6.8.6 末与 §6.10.3。三次运行的画面统计量差异很大：

   | 运行 | `faint` | `strong` | `blobs.count` | `background.share` | 渲染路径断言 |

   | `after`（dev，基线代码） | 16.47% | 9.17% | 844 | 11.8% | **未测** |

#### 6.11.4 判据修正：**换量纲，不是松阈值**

上一版判据是「绝对覆盖率 > 5%」，依据是「每帧可见节点 1 万 × π×2² ⇒ 上限 12%，重叠后 4~7%」。**该依据漏了一项**：节点被压进簇内，而**簇的屏幕半径**（`communityRadius(≤121) × zoom`）才是覆盖率的决定量；当时它只有 2.07px，节点几乎全叠在簇心。⇒ 覆盖率由**簇尺度**而非节点尺度决定，该期望模型有 ±2~3 倍不确定性，**拿它当硬阈值不诚实**。

| 层 | 判据 | 为什么可靠 |

| 机制层 | 节点屏幕半径 ≥ 2px 的占比 ≥ 95% | 缺陷的**直接观测量**，与任何阈值选取无关 |
| 可见层 | 覆盖率相对**同口径基线**的提升倍数 | 基线是**同一像素、同一裁剪窗口、同一段统计代码**测出来的 ⇒ 倍数可靠 |

#### 6.12.1 力模型与平衡半径：我这个注释**连着两版**都写了错公式

代码事实（`graphPhysics.ts:379-388`）：斥力 `F = repulsion·m_i·m_j/d²`（Barnes-Hut，远场整块当点质量）；重力 `fx += -gravity·x/|d|` ⇒ **大小恒定**；默认 `a = gravity/mass`，开 `gravityScalesWithMass` 后 `F = gravity·mass` ⇒ `a = gravity` 对全体一致。

| 版本 | 平衡半径式子 | 判决 |
|---|---|---|
| 教科书 | `gravity·d ≈ repulsion/d² ⇒ d=(rep/grav)^(1/3)` | ❌ 方程里没有 ∝`d` 的项 |
| **我第二版**（§6.11 写进源码的） | `R* ≈ √(6·repulsion·m²·N/gravity)` | ❌ m≈73 时**偏大 20.9 倍** |
| 可用版 | **`R* = √(repulsion·M/gravity)`**，`M = Σmᵢ`，`span* = 2R*` | ✅ 四组实测对账 |

第二版的错因：拿「圆盘内部均匀面密度」做解析积分 —— **二维下 1/r² 定律没有壳层定理**，边界处积分随源点趋近而发散，拿不到干净闭式。⇒ 纪律升级为「**只保留能用实测对账的式子**」。

对账（`calib-scan5.log`，同弹簧参数 sprK=0.04/spr=400；`M = 200×72.9 = 14580`）：

| g | rep | rep/g | 实测 span（8000 步） | `span/(2√(rep·M/g))` |
|---|---|---|---|---|
| 3.5 | 300 | 85.7 | 2513 | 1.12 |
| 5 | 400 | 80.0 | 2422 | 1.12 |
| 8 | 600 | 75.0 | 2608 | 1.25 |
| 8 | 1200 | 150.0 | 3494 | 1.18 |

⇒ `span ∝ (rep/g)^p`，两个干净对比给 **p = 0.53 / 0.59 ≈ 0.5**，与 `√` 相符；系统偏高 15%~25% 来自「团块非点质量 + 最外节点不在质量边缘」。**旧参数** `70000/0.01 ⇒ R* = 3.2e5`，而实测半跨度只到 `6.5e3` ⇒ **距平衡点 49 倍**（我在 §6.11 写的「500 倍」也是错的）。

#### 6.12.2 「社区呈环状」的真因：不是参数，是我新加的收敛闸**把布局冻结在环上**

登记时的推断是「恒定外向净斥力 + 归一化硬边界 ⇒ 最外层被钉在 `HALF_SPAN`」。**实测推翻了它**：终态世界半跨度只有 **791**（远小于 `HALF_SPAN = 1500`）⇒ 归一化**根本没触发**，边界约束不成立。

标定侧（圆盘播种）给出 `inner(<0.4R) = 0.16`（均匀圆盘理论面积比 `0.4²`），而生产 harness 的阶段 A 实测 **0.0027**（环）—— 两个数矛盾，于是写时间序列探针 `probe-4fix-stall.mjs`（同阶段内 t=40/70/100/130/160s 采样，页内直接读画布像素，不走截图）：

| 版本 | 世界跨度（5 个采样点） | `innerFrac` | 判决 |
|---|---|---|---|
| 改闸前 | 1583.16（**五点逐字节相同**） | 0.0057 / 0.0048 / 0.0048 / 0.0057 / 0.0048 | ❌ **布局被冻结**（渲染仍在跑：`arc` 789 万 → 3242 万） |
| 改闸后 | 1561 → 2278 → 2374 → 2304 → 2316 | **0.1572 / 0.1567 / 0.1228 / 0.158 / 0.1886** | ✅ 实心盘、收敛到标定平衡值 |

改闸后 `shape = rmsR/r95 = 0.699 / 0.732 / 0.717 / 0.696 / 0.691 ≈ 0.707`（均匀圆盘理论值），像素级**不同一** ⇒ 仍在演化。能永久关掉 `shouldRun` 的只有 `aggOver`（200 桶 ≪ 800 ⇒ 否）与 `settle.settled` ⇒ **就是那个闸**。

**闸本身错在哪**：第一版判据 =「布局 L∞ 半跨度的相对变化 < 0.004 连续 60 步」。它量的正是 `normalizeAggregateScale` 的**输出** —— 归一化一触发就把半跨度钉成 `AGG_LAYOUT_HALF_SPAN` 常数 ⇒ `relChange` 恒 0 ⇒ 60 步后**必然**判「已收敛」，与布局是否真的停了无关。**判据的量纲不能与另一个机制的副作用同源。**

第二版判据 =「最近 60 步内任一聚合节点的**累计位移 × zoom < 0.5px**」：量**输入侧**的量（位置）；换算到**显示量纲**（像素）语义就是「用户还看得见变化吗」；且用「相对**窗口起点**的累计漂移」而非「相邻两步之差」—— 后者对每步 0.049px 的匀速漂移判「静」，而 10 秒能漂 5px，肉眼可见。

⚠ **判形状的指标也要选对**：`shape` 对**厚环**不敏感 —— `0.4R~R` 的均匀圆环给 `rms/R = 0.762`，与圆盘的 0.707 只差 8%，而实测阶段 A 的 0.74 正是厚环。**`innerFrac` 才是敏感量**（圆盘 0.16 / 环 0.00）。我第一版把 `shape ≤ 0.80` 当判据，会误判成通过。

#### 6.12.5 本轮我自己的 6 处测量错误（全部当场更正）

> 口径注：本节按报告口径计 **6 条**；记忆侧 `MEMORY-DETAIL.md §73.5` 的同族清单计 **7 条** —— 多出的那条是「播种分布预设了要判的性质」，本报告把它记在 §6.12.2 与判据 #329 里。两处**不矛盾**，只是切分口径不同。
