## 四、对三项诉求的逐条核对

### 1. 定时启动荐股 / 趋势智选 建立候选池 —— ❌ 没打通

- **智能荐股**：`stock-recommendation` 分支会调 `recommender::run_recommendation_scan()`（`notify.rs:27`）。
  但 `reco_picks` 的**落库代码在 Tauri 命令里**（`stock_analysis.rs:4347-4379`，前端调用 `recommend_stocks` 才执行），
  引擎层 `recommender::recommend_stocks`（`mod.rs:362`）**不落库**。
  ⇒ 定时任务跑完**只有桌面通知，不产生候选池行**。
- **趋势智选**（serenity-screening，模板 version 53 存在）：**无任何专用定时入口**。
  只能靠 `SchedulerSettings` 手填通用 cron + `workflowId=serenity-screening`（且受 §三.1 持久化问题拖累）。
- **候选池的数据形态**：`reco_picks.seed_pool_json`（`[[code,name],...]` 快照）+ `pick_data`（完整 pick）。
  设计上还有一条 `recommend_stocks(preseed=Some(...))` 的「自动化管道从历史推荐构建候选池」通路
  （`mod.rs:358-360` 注释），但全项目 **preseed 零调用点** ⇒ 该通路从未接上。

### 2. 定时对候选池股票分析 —— ❌ 不存在

- 现有唯一定时分析 = `watchlist-scan`（**自选股**，非候选池）。
- 已有 `stock-pipeline` 模板（「发现 → 优先级评估 → 并发单股分析 + 持仓再评估」，`seed_stock_pipeline.rs`），
  但 `run_stock_pipeline_inner` **只被 Tauri 命令调用**（`core.rs:459`），无 cron/executor 调用；
  且模板 trigger = `Manual`。⇒ 只能手动点「立即运行」，7 条历史 run 有 4 条卡 running。
- `portfolio-scan`（持仓扫描）命令存在但无 UI、无分支 ⇒ 死。

### 3. 按 超短线/短线/中线/长线 间隔自动反思 —— ❌ 三层断点

反思链设计完整：分析落 `stock_reflections` pending（`hindsight_date = 分析日 + 期望持有期`）→ 6h 批量反思扫 pending → `compute_market_snapshot` 拉真实行情 → 跑 `stock-reflection` 工作流。
但实际：

| 层           | 现状                                                                                                                                                    | 证据                               |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------- |
| 队列         | 只有**批量路径**落 pending（`core.rs:1625`）；前端手动分析走 `run_stock_workflow_inner`，**不落 pending**；chat 路径 hook(`hooks.rs:848`) 亦无 9 月数据 | 9 月 17 条分析 → 0 reflection      |
| 调度         | 6h 硬编码服务在跑（`services.rs:2933`），但 cron 版 `batch-reflection`/`validate-decisions` 无执行分支                                                  | `cron_jobs` 0 行 + executor 无分支 |
| 结果         | 0 resolved、11 条 stuck running（7-28 起再无新行）                                                                                                      | DB 实证                            |
| **周期语义** | **不存在**。间隔取 LLM 输出的 `decision_expected_holding_days`（44 条中 **20 条为空** → 兜底 28 天）                                                    | DB 分布                            |

## 五、根因清单与修复方案

### P0 — cron 持久化（不修则其余全部白做）

`cron_job.rs` 用 **SQLite 方言**写 PG 库，且错误被 `let _ =` 吞掉：

- L351/L352：`DbBackend::Sqlite` + `json_extract(data,'$.created_at')`
- L382/L422：`INSERT OR REPLACE INTO cron_jobs …`
- PG 下应为 `ON CONFLICT (id) DO UPDATE SET data = EXCLUDED.data`、`data::json->>'created_at'`、backend 由 `db.get_database_backend()` 决定
- 所有 `let _ = self.db.execute_raw(...)` → `if let Err(e) = … { tracing::error!(…) }`

修后 `cron_jobs` 才能落库，重启不再丢任务。

### P1 — 打通「候选池 → 分析 → 排队反思」

1. **荐股 cron 落候选池**：把 `reco_picks` 落库从命令层下沉到 `run_recommendation_scan`（或让引擎层接收 `db` 并落库），使定时荐股真正产出候选池。
2. **新增 `pool-scan` task_type**：读 `reco_picks` 近 N 天（按 period/style 过滤、排除 `synthetic`、按 code 去重）→ 逐只 `run_single_stock_analysis`（该函数自带 pending 落盘）→ 一步同时满足诉求 ② 和 ③ 的队列入边。
3. **补齐/清理重复机制**：`batch-reflection` 与 6h 服务二选一（建议保留 6h 服务、把 cron 命令与 UI 删掉，避免「同一功能两条机制」）；若保留 cron 版，则补 executor 分支 + 前端入口。
4. **`validate-decisions` 参数落库**：`create_validate_decisions_cron` 的 `threshold/depth` 目前只拼进 `description`，未写入 `CronJob.prompt`（对比 `recommendation_cron` 的 JSON 存法），即使补了分支也拿不到参数。

### P2 — 周期语义与可用性

5. **4 周期 → 持有期映射**：`pool-scan` 分析时按候选行的 `period` 传 `default_holding_days()`（2/5/28/90）→ 生成的 pending 行 `hindsight_date` 自然落在对应间隔上；`stock_reflections` 建议加 `period` 列便于按周期统计。
6. **状态机自愈**：`running` 超过 N 小时回退 `pending`（现 11 条永久卡死）。
7. **趋势智选定时入口**：给 `serenity-screening` 加专用 cron 命令 + 面板，或把模板 trigger 从 Manual 改为 Schedule。
8. 前端 UI（`pool-scan` 面板）+ 11 语言 i18n 同步。
