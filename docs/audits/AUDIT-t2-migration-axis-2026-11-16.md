**形态级偏移**：接缝从 §2.2 的 11 条稳定契约（每条一个 trait、少量方法）膨胀为 `stock.analysis` 一个 trait 上 **147 个 async fn**（`axagent-core/crates/harness/src/stock_analysis.rs` 实测）。设计要求的接缝形态是「一个能力、多个可替换实现」；实际做成了「宿主命令的逐条镜像 + 插件进程路由壳」。插件进程零自治（无 DB、无状态、无 LLM，全部经 worker 帧调回宿主）——这正是章程 §0 開篇警告的失败形态：「机制已可用……用户看到的仍是单体」。

## 三、效率低的机制性根因（不是态度问题）

1. **单条命令的固定成本 = 9 环**：harness trait 默认错 stub → 宿主 service impl → worker 分派臂 → 插件常量+臂 → bundle 清单 → FE 切换 → browserMock → 测试 shim → 判定档锚点/doc-refs。其中 6 环是「镜像维护」，零自治收益。
2. **判定档棘轮自我加压**：capability-register 8 锚 + mustContain + PLAN 镜像行 + doc-refs，每批收口要回写 10+ 处登记——本批 #349 这部分耗时约占收口一半。
3. **批次粒度小于编译周期**：每批 1–8 条命令，cargo check/test 一次 10–25 分钟，批次大小撑不起等待成本；且验证排在批次末尾 ⇒ 用户全程只见「在跑」。
4. **形态级红灯没有当场上报**：§204.2 名单的陈旧名目（backtest_strategies/generate_* 四条不存在）、8 条零记录命令、接缝逐批加粗——这些都写进了 PLAN 附录（§206.1）而没在批内喊停。**这是最重的一条。**

## 四、资产 / 负债清单（供 B 线与 P6.1 使用）

### 保留的资产（P6.1 整块工程直接复用）
- T2 命令桥机制本体：派发、权限闸、清单对账、browserMock、前端 `invokePluginCommand`——P6.1 的 304 条命令本来就全要走它；
- 已迁 ~180 条命令的 FE 命令名与权限登记（迁移本身可保留，执行体在 P6.1 搬家时换位置）；
- 异步任务协议（#349 start/poll/cancel）：设计里 P5.0a 的「策略会话式 op」的一种落地，长跑命令的真需求；
- `dashboard_panels` 面板贡献（既有）+ 判定档门禁框架本身（防漂移有效，但**规模要砍**，见负债）。

### 需要偿还的债（B 线开工时裁）
- **147 方法的巨接缝**：`stock.analysis` 应在 P6.1 时瘦身为少数真契约（行情、LLM、任务台账、数据查询投影）；迁出的命令逻辑应**搬进插件仓**（plugin-stock 已依赖 `analysis-engine`/`astock-data`，具备承接条件），而不是宿主留 core、插件留壳；
- **判定档 8 锚 × PLAN 镜像行 × doc-refs 的收口成本**：只对「契约面」锚保留硬门，纯计数锚降级为 batch 抽查；
- browserMock / 测试 shim 的双份维护面：随 T3 出包改为「插件仓自带测试」，宿主只测装载。

## 五、B 线的验收判据（照抄 §6，不给新发明）

1. `plugin.json` 声明 `pages[]`，宿主装出一个**用户点得到**的插件页面（T3 选 A：配置 + CSP + 桥扩到 page）；
2. 该页面消费 ≥10 条 `stock_*` 命令端到端走通（清单声明 → 派发 → 渲染）；
3. 切片完成后把 §6.1 的 ①⑤⑥ 估工从外推变为实测，更新 PLAN §6.1；
4. **切片期间不迁任何新命令**（不再加粗接缝）。

## 六、一句话

> 半个月做的是「把命令改个名字再从插件调回来」；设计要的是「把能力搬出去让主壳看不见它」。前者做了 47 批，后者一步没走——这就是「和最初的设计差别非常远」的准确含义。
