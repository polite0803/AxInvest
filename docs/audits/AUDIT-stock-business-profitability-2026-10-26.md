⇒ 即：**顶层「买入」在当前主档口径下不可达** ——
即便某档算出了买入，顶层也只输出持有（可执行档优先分支）或观望（四档不可执行分支）。

#### 层四（⭐ 2026-10-26 补）：**校准死循环** —— 真正的主因

前面三层加起来只能解释一半。**实测的量化事实**：

| 量 | 值 |
|---|---:|
| 多档分析里 `calibrationReady=false` | **147 / 160（92%）** |
| 触发降级的规则 | `R-CALIB-CAP`（校准未达标 ⇒ 置信被压到 `cap_floor=60` ⇒ 动作联动降级） |
| 校准门槛 | `CALIBRATION_MIN_SAMPLES = 30`（**每档**独立判定） |
| `strategy_performance` 全表 | **45 行** |
| 逐档已判定样本 | short **18** / mid **7** / ultra **7** / long **0** |

⇒ **四档全部 < 30 ⇒ 校准永远不达标 ⇒ 置信永远封顶 60 ⇒ 动作永远被压成持有 ⇒ 顶层 0 买入。**

**⇒ 而 0 买入 ⇒ 没有新的决策样本 ⇒ `strategy_performance` 不增长 ⇒ 回到起点。**

#### ⭐ 层五：死循环的**唯一出口**被一道过严的判据堵住

`require_pool_snapshot_coverage` 要求建池**两源**快照齐全，而实测：

| 决策日 | 池快照源数 | 之后 K 线根数 | 档位成熟 |
|---|---:|---:|---|
| 2026-05-27 | 1（只有 industry） | 100 | **T+90 ✅** |
| **2026-06-10** | 1 | **90** | **T+90 ✅**（边界） |
| 2026-06-11 | 1 | 89 | T+28 ✅ |
| 2026-08-18 | 1 | 42 | T+28 ✅ |
| 2026-09-04 | 1 | 29 | T+28 ✅ |
| 2026-09-07 | 1 | 28 | T+28 ✅（边界） |
| 2026-09-28 起 | 2 | ≤14 | T+5 only |

**关键机制（实测 + 源码）**：档位成熟判定只看「**行情库里决策日之后有没有 N 根 K 线**」，
**不看今天**（`compute_market_snapshots` 取最近 500 根、`exit_idx = entry_idx + expected_days`）
⇒ **回放一个足够早的 as_of 日，long 档当场就能成熟。**

⇒ 旧判据把这 7 个日期全部排除 ⇒ **long 档校准样本只能等 wall-clock（T+90 ⇒ 2027-01）**，
而门槛又不允许降 ⇒ **长期档永远校准不了** ⇒ 死循环闭合。

**⇒ 已实施**：判据放宽为「**至少一源**」（两源都缺仍排除：那时池子 100% 是静态
`FALLBACK_STOCKS`，不是「当时的候选池」）。详见 `PLAN-r3h-long-sample-calibration.md`。
⇒ **「买入→观望」与「买入→持有」的风控否决共 10 次，是「买入」消失的直接拦阻者。**

### 2.3 为什么这比 α 更硬

**α 问的是「历史选股有没有超额」；这里问的是「系统现在还会不会开仓」。**

- 即使某天 α 转正，**顶层不产「买入」⇒ 没有任何可执行动作产生收益**；
- 更关键：**这同时让「盈利能力样本」无法自然产生** ——
  `decision_validations` 的可执行样本来自 `decision_action='buy'`，
  顶层 0 买入 ⇒ **新的买入样本不会自动积累**（与 §5 的 cron 停摆叠加）。

⇒ 这不是「样本不够」，是**功能处于实质关闭状态**。

### 2.4 与 10-25 裁决 §13.3 的关系（**修正旧解释**）

10-25 裁决写的是「10-18 之后两代全部 0 买入（`主档=` 标记最早出现在 10-18）」。

**今天实测的三处修正**：
1. **边界前移 2 天**：tv=157（**10-16**）起就 0 买入，tv157/158 尚无 `主档=` 标记 ⇒ **主档标记不是 0 买入的起因**；
2. **主档标记是「维持现状的装置」不是「起因」**：142 条带标记行顶层买入本就全 0，
   它的作用是把顶层固定在持有/观望；
3. **真正的起因是四道否决门 + 主档口径的组合**，
   而否决门的存在被 `dataGaps` 原文**逐条留痕**（不是静默吞掉）。

**⇒ 旧结论「0 买入 = 模板换代副作用」应改为「0 买入 = 风控/估值/情绪三门 + 主档口径的现行设计」** ——
**这是产品决策，不是 bug**（改不改是用户的裁决权，但必须先知道它在拦什么）。

| `reflection-validated.params` | **空对象 `{}`** |
| `reflection-validated.result` | **null** |

  第 1 步  if let Some(params) = obj.get("params") { return params.clone(); }

### 5.1 ⚠️ 本条经历了一次**自我误判**，值得单独记（我第一版写成「cron 从未执行过 ⇒ 机制空转」）

我的推理链：查 `cron_jobs` → 看到 `run_count=0` / `last_run_at=null` ⇒
查 `cron_job_history` → 该任务 0 条（而其它 cron 有 3~103 条）⇒
**判定「播种了但调度器从不触发它」= 缺陷 R-3k。**

**错在哪**：我把「**从未执行**」当成了「**无法执行**」——
**没有核对 `next_run_at` 与当前时间的先后**。这个 cron 是 25 日深夜才播的种，
第一个触发点就是今天早上 08:30，**在读数时点（06:37）还没到**。
⇒ 0 条历史是**预期的**，不是异常。

**与既有判据同族**（本项目已多次踩）：
- 「0 命中 ≠ 没问题」（判据 #7）：审计脚本自身会撒谎；
- 「日志缺失 ≠ 分支为真」；
- **本条新增**：「**`run_count=0` ≠ 任务不跑**」——必须同时看 `next_run_at` 与 `created_at`，
  才能区分「还没到点」/「到点但没跑」/「压根没播种」**三种**状态。

**⇒ 我上一版把 R-3k 登记成 P0 缺陷是错的**：
若按那个结论去「修」，会去改一个没有问题的调度器。**这条误判已从本文撤销。**

## 9. 复现方法

```bash
# 全部读数可用一条命令重跑（本文所有 SQL 均在 .workbuddy/tmp/）
node scripts/pg-connect.mjs sql "<SQL>"

# 关键脚本
.workbuddy/tmp/final_alpha.sql   # 配对 α（严格口径）
.workbuddy/tmp/strict_live.sql   # 实盘严口径读数 + t 检验
.workbuddy/tmp/tv2.sql           # 按模板版本的买入率
.workbuddy/tmp/hz9.sql           # 顶层动作 × 档内买入交叉表
.workbuddy/tmp/hz6.sql           # 否决措辞分布
.workbuddy/tmp/main3.sql         # 主档两分支 × 顶层动作
.workbuddy/tmp/orph.sql          # 孤儿验证行
```

**⚠ 取证注意**（本轮踩了 4 次）：
1. `pg-connect.mjs sql` 会**过滤以 `--` 开头的参数** ⇒ SQL 开头必须有空格或不能以注释开头；
2. **中文注释会触发 UTF8 编码错误**（`无效的 "UTF8" 编码字节顺序`）⇒ 注释用 ASCII，或用 `chr(0xXXXX)` 拼中文字面量；
3. **代际判据必须用 `purpose` 关联 `reco_picks`**，不能用 `as_of_date IS NULL`（live 行的 `as_of_date` 也非空）；
4. **实盘买入的分组日必须用 `generated_at`（决策日）**，用 `created_at`（回填日）会得到相反符号的结论。
