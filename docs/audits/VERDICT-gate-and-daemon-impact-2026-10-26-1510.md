## 1. 回答 ①：三门放开的价值会体现在什么方面

### 1.1 先说结论

> **放开三门的价值 = 让顶层「买入」信号能产生，从而让盈利能力样本能自然产生。**
> **它不能创造 α，只能把 α 从「测不出来」变成「可测」。**
> **且目前无法用已到期数据证明放开是对的 —— 24 条候选里只有 1 条持有期已到期。**

### 1.2 三门实际拦下多少

`horizon_decisions[*]` 里 `originalAction=买入`（即通过评分、入场门后的原始结论）共 **24 条**：

| 处置 | 条数 | 说明 |
|---|---:|---|
| **保留为买入** | **9** | 档内买入成功（short 3 / mid 3 / long 3） |
| **被三门改写** | **15** | long 8（持有 1 / 观望 7）、mid 3（持有 1 / 观望 2）、short 4（全持有） |

**15 条被拦下的，100% 是「本档风控否决」（`dataGaps` 原文）**，措辞分布：
- `本档风控否决:买入→观望(本档风险档=极高风险)` —— 9 次
- `本档风控否决:买入→持有(本档风险档=高风险)` —— 6 次

**⇒ 注意：市场情绪否决与估值否决这 10+8 次，在 10-16 之后的档级数据里已经查不到**
（`originalAction=买入` 的 24 条里没有一条带情绪/估值否决措辞）
⇒ **当前形态下真正拦阻「买入」的是风控门（风险档），情绪门与估值门对买入已不再起作用。**

### 1.3 价值体现在四个可验证的方面

| # | 价值 | 现状 | 放开后的可观测变化 | 当前能否验证 |
|---|---|---|---|---|

### 1.4 ⚠ 但价值有一个硬上限：**放开只能让 α 变得可测，不能让 α 变正**

**⇒ 真正的赚钱要靠 ① 之外的机制（择股能力本身），三门只是把闸门从「关着」变成「开着」。**

## 2. 回答 ②：剥离为常驻调度对后续项目修改的影响

### 2.1 🔴 先更正你的第②点前提：**回放 cron 今天确实触发了，但失败了**

14:40 我写「cron 零执行」——**在 14:40 那个时点是对的**（应用未启动）。
**但 14:59:05 GUI 应用启动后，调度器立刻补跑，今天共 9 个任务被触发**：

| 触发时刻 (BJ) | 任务 | 结果 |
|---|---|---|
| 14:59:13 | opc-demand-discovery-daily | ✅ 289s |
| 15:00:13 | trend-screening-daily | ✅ 285s |
| 15:01:13 | stock-reco-daily | ✅ 273s（**"本次未发现符合条件的新推荐"**） |
| 15:01:43 | decision-backtest-daily | ✅ 35s（written=41 skipped=623） |
| 15:02:17 | intent-expiry-daily | ✅ 7ms |
| 15:02:47 | stock-analysis-rerun-daily | ✅ 让路（已有批次在跑） |
| 15:03:17 | mover-recall-analysis-daily | ✅ 发起 batch_id=`c6fac351…`（**至今 running**） |
| 15:03:47 | universe-code-scan-daily | ✅ 5s |
| **15:05:17** | **time-travel-batch-daily** | ❌ **失败：「回放日 20 个（成功 0 / 失败 20）」** |

**⇒ 你的观察（"后台进程已运行 6h5m、API 消耗确认在跑"）与库内证据一致，但归因要修正：**
**那个长跑进程是 `mover-recall-analysis-daily`（15:03 发起，仍 `running`），不是回放。**
**⇒ 而回放 cron 失败的直接原因，就是被它抢了同一把锁。**

### 2.2 根因链（已逐环验证）

```
15:03:17  mover-recall-analysis-daily 发起 batch c6fac351（status=running, total=60, scanned=284）
          ⇒ 持有 state.time_travel_batch_lock（try_lock_owned，进程级）
15:05:17  time-travel-batch-daily 触发 ⇒ 列出 20 个可回放日
          ⇒ 对每个日调 run_time_travel_batch_inner
          ⇒ 全部 Err(ALREADY_RUNNING)  ← try_lock_owned 失败
          ⇒ fail_days = 20 ⇒ 记 success=false「20 个回放日失败」
```

**证据**：
- `services.rs:3531` `run_time_travel_batch_inner(...)` 的 Err 分支 `fail_days += 1; continue;` ⇒ **不写任何批次行**（实测 `time_travel_batch_runs` 今日 0 新行）⇒ **失败信息只存在于 `cron_job_history.output`，不留批次痕迹**。
- `mover_recall_analysis.rs:367` 与 `time_travel_batch.rs:731` **用的是同一把 `state.time_travel_batch_lock`**。
- `error_code.rs:358` `TIME_TRAVEL_BATCH_ALREADY_RUNNING` / `:372` `MOVER_RECALL_ANALYSIS_ALREADY_RUNNING`。

### 2.3 🔴 剥离为常驻调度的**真实价值**：证据在 `mover_recall_analysis_batches`

| 批次 | 状态 | 消息 |
|---|---|---|
| `c6fac351…` (15:03) | **running** | — |
| `5fcc3dfd…` (10-25 23:43) | **interrupted** | 「应用重启：补分析批次运行中进程退出，**as-of 封闭世界无法跨进程续跑**」 |
| `a198fd98…` (10-24 11:33) | **interrupted** | 同上 |
| `73515aa9…` (10-23 06:00) | **interrupted** | 同上（fail=32） |

**⇒ 连续 3 次长任务因「应用重启 / 进程退出」被腰斩。**
**⇒ 这就是「GUI 进程当宿主」的代价：**
1. **应用一关，所有在跑的长任务全部作废**（as-of 封闭世界不可跨进程续跑 ⇒ 只能整批重来）；
2. **错过的档期永久丢失**（`resumed_next_run` 只补发**一次**，不逐档回溯）；
3. **调度器与用户操作争同一把锁**（今天 15:03 vs 15:05 就是现场）。

### 2.4 剥离为常驻调度的**影响面**（逐项核实，不是推测）

| 维度 | 事实 | 影响 |
|---|---|---|
| **调度器本体可否脱离 Tauri** | ✅ **可以**。`src-tauri/crates/runtime/src/cron/scheduler.rs`（208 行）**零 `tauri` 引用**；`runtime` crate 的 `Cargo.toml` **零 tauri 依赖**；executor 通过 `set_handler` 注入回调 | **不需要重写调度器**，只需提供一个能构造 `AppState` 等价物的宿主 |
| **业务 handler 可否脱离 Tauri** | ⚠ **部分**。`services.rs` 的 handler 需要 `work_engine` / `astock_client` / `db` / `vector_store` / `master_key` / `trajectory_storage`；`AppState` 本身**零 tauri 引用**（`app_state.rs` grep 无命中） | **可复用**，但要把 `AppState` 的构造从 Tauri 初始化里剥出来（`init/state.rs:1803` 已有 `time_travel_batch_lock` 等） |
| **双实例风险** | 🔴 **没有 leader lock / advisory lock**（全仓 grep 零命中）。DB 里有 `cron_jobs` 单表 ⇒ **两个进程会同时读到同一批任务并各自派发** | **必须加** PG advisory lock 或单例租约，否则「常驻 + GUI 同时开」= 任务跑两遍 |
| **任务互斥** | ⚠ `time_travel_batch_lock` 是**进程内** `Arc<tokio::sync::Mutex<()>>` ⇒ **跨进程无效** | 常驻进程与 GUI 进程可以**同时**跑回放 ⇒ 落库冲突（`uq_reco_picks_business_key` 会撞，但要靠捕获冲突重试兜） |
| **live 时间窗判据** | ✅ `in_live_window()` 是纯函数（按北京时间），与进程无关 | 无需改 |
| **Windows 常驻方式** | ⚠ 仓库**无任何服务化设施**（无 `windows-service` 依赖、无 `.service`/计划任务定义）。Windows 上落地需 NSSM / 计划任务 / `schtasks` | **新增工作量**，不是"改个地方" |
| **对后续业务修改的影响** | ✅ **小**。调度器与业务层已通过 `set_handler` 解耦；`runtime` / `runtime-core` 是独立 crate | 业务代码照常改；只有"谁提供 AppState"这一处要改 |

### 2.5 我的建议（按代价/收益排序）

| 方案 | 代价 | 收益 | 评价 |
|---|---|---|---|
| **A. 只做「应用常驻」**（把 GUI 应用最小化到托盘 / 加开机自启） | 极低（配置项） | 解决"错过的档期永久丢失" | ✅ **先做这个**。它解决 80% 的问题且不动架构 |
| **B. 加 advisory lock + 把回放 cron 挪出 live 冲突窗口** | 中（1 处 SQL + 1 处调度） | 解决"双实例"与"被 mover-recall 抢锁" | ✅ **必做**（双实例是正确性问题，不是体验问题） |
| **C. 完整常驻 daemon**（独立 binary + Windows 服务化） | 高（新增服务化设施 + AppState 剥离） | 解决"应用关闭时长任务腰斩" | ⚠ 值得，但**在 A+B 之后**再做 |
| **D. 改三门**（产品决策） | 中（改 `apply_risk_veto` + 模板升版） | 让顶层能出买入 | ⚠ 独立议题，**不因 R-3w 而做** |

**⇒ 对「后续项目修改」的影响，核心一句话：**
**剥离调度器**不会**增加**业务改动面（`runtime` crate 已零 tauri 依赖，handler 是回调注入），
**只会新增两处必须正确处理的东西**：**跨进程互斥（leader lock）** 与 **Windows 服务化落地**。
**⇒ 反倒是「现在不剥离」会持续产生修改面**：每有长任务（如 mover-recall 60 只 / 回放 20 日）就有被应用重启腰斩的返工。
