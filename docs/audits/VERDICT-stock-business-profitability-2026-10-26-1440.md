## 5. 🔴 我 06:30 的判断被推翻：回放 cron **08:30 没触发**，而且原因不是「还没到点」

### 5.1 事实

| 证据 | 值 |
|---|---|
| `cron_jobs` 里 `time-travel-batch-daily` | ✅ 存在，`schedule = 30 8 * * *`，`status=active` |
| **`run_count`** | **0** |
| **`last_run_at`** | **null** |
| **`next_run_at`** | **0**（不是「明天的时刻」） |
| `created_at` | 2026-10-25 23:39:50 |
| `updated_at` | **2026-10-26 08:51:33** |
| `cron_job_history` 该任务 | **0 条** |
| **`cron_job_history` 今日全部记录** | **0 条**（最后一次是 2026-10-25 23:49，trigger=`system`） |

**⇒ 06:30 我写「首次自动触发在今天 08:30 ⇒ 样本从今天起自然增长」—— 今天是 14:40，08:30 早已过去，
但 `run_count=0`、`last_run_at=null`、`cron_job_history` 零条 ⇒ 没触发。**
**⇒ 这是 06:30 那版裁决的**一处明确错误**（我当时只核了「还没到点」，没等它到点后复核）。**

### 5.2 归因：**不是调度器 bug，是宿主进程没在跑**

| 判据 | 证据 |
|---|---|
| 调度器是**进程内**组件 | `services.rs:4292` `tauri::async_runtime::spawn(scheduler.start())` —— 挂在 Tauri 应用生命周期里，**应用不启动就没有调度循环** |
| 独立宿主二进制 | `src-tauri/src/bin/` 只有 `axagent-batch-rerun.rs` / `axagent-validate-backfill.rs`；**没有常驻 daemon** |
| 进程实况 | `Get-CimInstance Win32_Process` 全表扫描：**无 `axinvest` / `axagent` 进程**（只有 `npm run tauri dev` 的 vite + 正在编译的 `rustc --crate-name axagent_lib`） |
| 今日库内写入来源 | 05:05（10-21 批次）、05:12（09-28 批次）、08:55（06-10 批次）—— **全部是我自己跑 CLI 产生的**，与 cron 无关 |

### 5.3 ⚠ 还有一个更硬的问题：`next_run_at = 0` ⇒ 调度器**不派发**

源码 `runtime-core/src/cron_job.rs`：
```rust
// 调度器只认 next_run_at 到期，不再做表达式匹配
.filter(|j| j.is_active() && j.next_run_at.is_some_and(|next| now >= next))
```
`next_run_at = Some(0)` 时 `now >= 0` 成立 ⇒ **会**被派发；
但 `resumed_next_run` 的三态策略是：
```rust
match current {
    Some(next) if next > now_ms => Some(next),   // 未来 → 保留
    Some(_) => Some(0),                           // 过期/0 → 置 0，首轮 tick 补发一次
    None => calculate_next_run(schedule, now_ms), // 从未编排 → 当场算
}
```
**⇒ 该任务 `next_run_at=0` ⇒ 重启后会「补发一次」⇒ 下次应用启动时它会跑（一次性）。**
**⇒ 但 `next_run_at` 至今仍是 0、`run_count` 仍是 0 ⇒ 说明今天**没有一次「应用启动 ⇒ 调度器装载 ⇒ 首轮 tick」**发生过。**

### 5.4 结论（这才是真正的机制问题）

> **回放 cron 不是「缺一个 Windows 计划任务」，而是「依赖桌面应用常驻」。**
> **应用关着 ⇒ 每天 +1 的回放日就不会发生 ⇒ 校准样本不会自然增长 ⇒ 死循环不会破。**
> **⇒ 昨天的裁决把「cron 已就位 ⇒ 样本自然增长」当成了既有事实，**这一条被今天的实测推翻**。**

**⇒ 登记新缺陷 R-3w（P1）：**`time-travel-batch-daily` 的调度宿主是 GUI 应用进程，
应用不常驻 ⇒ 每日回放不发生；且 `next_run_at` 长期为 0 ⇒ 恢复语义依赖「下次启动补发一次」，
**该语义本身只补一次，不是「每天补」** ⇒ 中间关机的日子永久丢失。

## 9. 复现方法

```bash
node scripts/pg-connect.mjs sql "<SQL>"
# 辅助执行器（解决 pg-connect 过滤 "--" 开头参数）：
node .workbuddy/tmp/runsql.cjs .workbuddy/tmp/strict_live_v2.sql
```

关键 SQL（均在本目录）：`strict_live_v2.sql`（严口径）、`final_alpha.sql`（配对 α）、
`live_dist.sql`（分布/尾部）、`calib_tiers.sql`（逐档样本）、`g1_tv.sql`（版本换代）、
`buy_now.sql`（顶层买入）、`cron_hist_today.sql`（cron 执行史）。

**⚠ 取证注意（本轮新增）**：
1. `pg-connect.mjs sql` **过滤以 `--` 开头的参数** ⇒ SQL 需前导空格（`runsql.cjs` 已封装）；
2. **时间列类型不统一**：`cron_jobs`/`stock_analyses`/`stock_reflections`/`strategy_performance` 是 **epoch 毫秒 bigint**，
   `decision_validations`/`reco_picks` 是 **text ISO** ⇒ 混用会报 `无效的 bigint 输入语法` 或 `操作符不存在`；
3. `chr()` 拼中文要写 `chr(0x4E70) || chr(0x5165)`（**`+` 是数值加法会报 `text + text`**）；
4. `left(timestamp, n)` 不存在 ⇒ 用 `(expr)::date`。
