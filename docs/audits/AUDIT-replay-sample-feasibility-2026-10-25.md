# 时间旅行生成样本方案可行性评估 — 2026-10-25

> 问题：「用时间旅行解决样本问题，代码稳定后快速生成样本」——这个思路在现行基础上是否可行。
> 前置：`AUDIT-stock-profitability-verdict-2026-10-25.md`（盈利性裁决）已认定当前无证据表明能赚。
> 本文只评估「回放生成样本」这条路径本身，不改代码。

---

## 0. 结论

**可行，但结论要修正三处。** 回放基建比你预期的成熟得多（这点你可能低估了自己已建成的东西）；
但它**修不了选股层**，且会让样本**系统性偏乐观**——这两个问题不解决，回放出来的样本
只会让你更快地得到一批更可信地错的读数。

| 判断项 | 结论 |
|---|---|
| 回放基建成熟度 | ✅ **够用**。能力申报 + 时间边界不变量测试 + 降级分档 + 批量引擎都在位 |
| 回放样本/实盘样本隔离 | ✅ **已实现**。`analysis_kind` / `synthetic` / `as_of_date` 三件套，闭环只吃实盘 |
| 回放能否重建分析层 | ✅ 可以，行情类可深回放 |
| 回放能否重建**选股层** | ❌ **不能**。且用今天的自选股回放历史日 ⇒ 前视偏差，方向为正 |
| 回放数据深度 | ⚠ **分层**。行情类可多年；news/舆情/榜单类受限于 2026-09 起点 |
| 是否会诱发过拟合 | ⚠ **必然**。回放样本会从验证集退化成训练集，且退化不可见 |
| 前置验证是否已做 | ❌ **没有**。缺「回放 vs 实盘同一天」一致性校验 |

## 1. 已经就绪的部分（先确认这些，避免重复建设）

这是本评估里唯一的正面结论，且有明确出处。

### 1.1 回放样本与实盘样本**已经物理隔离**

`src/commands/stock_workflow/core.rs:640-663` 落库时写入：

```rust
analysis_kind: Set(AnalysisKind::from_asof(as_of_date.is_some()).as_storage().into()),
as_of_date:   Set(Some(current_as_of.clone())),
synthetic:    Set(if as_of_date.is_some() { 1 } else { 0 }),
```

`core.rs:461-520` 进一步保证：回放的覆盖目标只认 `(stock_code, as_of_date, kind='replay')`，
不同 as_of 则新建版本行（INSERT + parent 指向原记录），**不会覆盖实盘行**。

⇒ 你担心的「早期版本数据变脏」，在**落库层**已经被挡住了。

### 1.2 闭环权重只吃实盘样本

`crates/analysis-engine/src/recommender/reco_loop.rs:357-358`：

```rust
let rows = decision_validations::Entity::find()
    .filter(decision_validations::Column::AsOfDate.is_null())
```

⇒ 回放产生的 `decision_validations` 行（`as_of_date` 非空）**永远不进入**权重校准。
这正是「回放只用于评估、不用于训练」的正确架构——**已经实现了**。

### 1.3 先验在回放时按截止日递归截断

`crates/analysis-engine/src/horizon_prior.rs:183-197`：

> as-of 版先验：只用**截至 `as_of` 已知**的结算样本（`None` = 实盘口径）。
> 拿全量先验去回放等于让未来信息参与历史决策。

⇒ 回放 8 月某日时，只看到 8 月前已结算的样本。这是**递归式时间旅行**的正确语义，
不是「拿今天的先验跑昨天的数据」。这一层做得对。

### 1.4 取数侧的 as-of 能力体系

`PLAN-asof-gaps.md` P1–P5、T1–T20 已把 D 桶（时间泄露）6 组修完，且建立了：

- 能力申报三态：`NativeDateParam` / `Fallthrough` / `SynthesizeFromKline`，**申报≠实现即违规**
  （`get_index_quotes_with_asof` 的 trait 默认已改为显式失败，就为堵这个）；
- **时间边界不变量测试** `asof_boundary_tests`（8 条，替身零网络）：对固定截止日跑取数面，
  断言每个返回项日期 `<= 截止日`。这是「新增取数方法漏接 as-of」的通用护栏；
- 降级三档 `Failure` / `NoData` / `StructuralGap` —— 让「接口挂了」与「这个维度回放本就不适用」
  不再长得一样。

### 1.5 批量引擎已有

`src/bin/axagent-batch-rerun.rs:69-88`：`--since/--until/--codes/--limit/--template-version/
--only-stale/--reflect-after/--backfill-reflections`。**但它是 rerun 已有记录，不是生成新样本**
（见 §2）。

## 2. 限制 A（致命）：回放修不了「选股层」

### 2.1 事实

`axagent-batch-rerun` 的全部筛选参数（`--since` / `--until` / `--codes`）筛的都是
**库里已存在的 `analysis_date`** ⇒ 它只能在「当初被选中的票」上重跑分析，**不能在任意历史日期
凭空生成一批新候选**。

候选池四路种子（`AUDIT-stock-accuracy-2026-10-24.md` §2）：user / mover / reflow / miss。
逐路可回放性：

| 种子 | 来源 | 可回放？ |
|---|---|---|
| user（自选 ∪ 本机标的） | `refresh_user_seed_db` → `watchlist_items` + `market_stock_universe(origin='local')` | ❌ **无时间维度** |
| mover（当日涨幅榜） | 可从 `market_daily_close` 按截止日重算 | ✅ |
| reflow（回灌） | 事件表，可重算 | ⚠ 需核 |
| miss（漏检反证） | 核查结论表 | ⚠ 需核 |

### 2.2 后果：一个必现的、方向为正的前视偏差

`src/commands/stock_analysis.rs:4792-4819`：

```rust
pub(crate) async fn refresh_user_seed_db(db: &DatabaseConnection) -> usize {
    match reco_seed::load_watchlist_items(db).await { ... }        // ← 当前自选，无 as-of
    match reco_seed::load_local_universe_items(db).await { ... }   // ← 当前本机标的
    axagent_meta::recommender::set_user_seed(items.clone());       // ← 全局状态
}
```

`watchlist_items` 与 `market_stock_universe` 都**没有历史快照**（全库搜
`watchlist_snapshot` / `watchlist_history` 零命中）。

⇒ 回放 2026-08-01 时，候选池里塞的是**2026-10-25 的自选股**。
而那些票是你 8 月到 10 月之间——看了推荐、看了涨幅榜之后——才加进去的。
**等于把未来信息注入过去的选股。**

⇒ 偏差方向**确定为正**：事后觉得值得关注的票，回放里的表现天然好于当时真正会进池的票。
**回放生成的选股样本会系统性高估收益，且幅度无法估计。**

顺带：`set_user_seed` 是进程级全局，多个 as-of 并发回放会互相覆盖 user seed
（与 `as_of.rs` 里 `AsOfScopeStack` 修掉的那类「全局残留」同族）。

### 2.3 这是一个「补不了只能等」的空缺

要日后能回放选股层，必须**从今天起**每日落一份 `watchlist_snapshot`。
但那是「从今天开始积累」，**不是「回放过去」**——这个悖论无解：
你无法重建一个当时没记录的决策输入。

⇒ **结论：时间旅行能加速「分析/决策层」的验证，不能加速「选股层」的验证。**
而盈利性裁决里 127 单成熟样本的分母，主要由选股 + 决策共同决定。
所以回放能把样本量从 127 推到几百，但**推不出「选股链对不对」这个答案**。

## 3. 限制 B：数据深度分层 —— 越往前回放，信息越残缺

| 数据面 | 历史深度 | 依据 |
|---|---|---|
| K 线 / 行情 / 估值 | 可多年（vendor 原生日期参数） | `NativeDateParam` 一族 |
| 资金流 | 可回溯（sina 日历史） | `PLAN-asof-gaps.md` §23.1 |
| 财报 | 可回溯，但**有追溯调整**（见 §3.1） | `truncate_financials_by_asof` |
| 新闻 | **2026-09 起**（`news_archive` 无回填工具，P6 未立项） | 同 §5 |
| 舆情 / 热股榜 / 行业榜 | 当日快照或合成，**不可深回放** | §10.1、§21.1 |
| 概念/行业归属 | 容忍当日值（慢变量） | §10.1 |

⇒ 回放到 2026-09 之前，`news` 一族**结构性为空**。而空数据会走静默降级，
降级又会把决策推向偏乐观——`portfolio-mgr.rhai:554-597` 的「缺财务数据判低风险」
正是 2026-10-24 刚修掉的那一类。

⇒ **回放早于 2026-09 得到的样本，反映的是「数据缺失下的决策」，不是「真实历史决策」。**
这种样本能进分母，但必须单独打标、单独统计，否则就是换了个形式的污染。

### 3.1 财报的追溯调整（文档未提及，但真实存在）

回放 2024 年某日时，`get_financials` 返回的是**今天库里的财报值**——而财报会被更正、
重述、追溯调整。用更正后的数字去回放更正前的决策，是**信息泄露**，方向不确定但存在。

`truncate_financials_by_asof` 只按**报告期**截断（哪一期已发布），
**不处理同一期被事后修订**。若要严谨，需要"财报快照"（每期首次披露值），当前没有。

## 4. 限制 C：回放可用 = 过拟合的入场券

你说「代码稳定后快速生成样本」。这个前提在实践中会自我瓦解：

1. 一旦 5 分钟能生成 200 单，**「再改一版看看回放会不会更好」就变成不可抗拒**；
2. 此时回放样本从**验证集**退化成**训练集**，你测的是「这版代码在历史上的拟合度」；
3. **退化过程不可见**——你只会觉得自己在"科学迭代"，每次都有数字支撑。

这就是回测过拟合（Bailey / López de Prado 的 PBO）。它比"没有数据"更危险，因为
它给你**虚假的确定感**。当前的 1,145 行提前窗口污染已经是这个病的温和版：
那批数据当时也让所有指标"看起来正常"。

⇒ **对策只能是纪律，不是代码**：预注册 + 一次性开盒（见 §6）。

## 5. 缺一个前置验证（现在完全没做）

**回放-实盘一致性校验**：挑有实盘记录的日期（如 2026-10-20），
用回放跑同一天，逐项对比回放产出 vs 实盘产出（`stock_analyses.decision_json`）。
全库搜「回放 重演/复现/一致性/等价」**零命中** ⇒ 这个校验不存在。

为什么必须先做：没有它，你无法区分「回放产生的样本」与「1,145 行提前窗口污染」——
两者都是**看起来正常、实际不可信**的数据。这是同一形态的教训。

通过标准（建议）：同一天同一票，回放的 `action` 与实盘一致率 ≥ 80%，且
`confidence` 偏差中位数 ≤ 5；否则说明回放重建不忠实（多半是 §3 的数据残缺或
§2 的种子偏差），样本不可用。

### 5.1 附：这类工具会静默产出假样本（已实测过一次）

`crates/astock-data/src/as_of.rs:64-70` 记录的事故：

> 2026-09-23 实测（`axagent-batch-rerun --since 2026-07-21 --apply --reflect-after`）——
> 4 条 as-of(2026-07-21) 分析全部 `completed` 且落库正确，但紧随其后的批量反思
> 拿到的 K 线被截断在 07-21 ⇒ 4/4 报「在 2026-07-21 之后无K线数据」⇒ 降级为无行情反思
> ⇒ `deterministic_was_correct` 恒 `None` ⇒ **一条 `strategy_performance` 都不写**，
> 反思→规则→反哺闭环整体空转 —— **而日志里每条分析的结论都"正常"**。

已经用 `AsOfScopeStack`（token 精确出栈）修掉。但它说明：**批量回放的污染是批次级的**，
一次错几百单，且全程静默。§5 的一致性校验就是防这个的探针。

## 6. 正确用法：顺序不能反

### 6.1 先修尺子，再量长度

盈利性裁决里的 G4（成本扣减 + 净胜率口径统一）必须**先于**回放做。
理由：`hit_rate_backtest.rs:268` 不扣成本、`:172` 判 `ret > 0.0 → hit`，
且全仓存在 42.5% / 54% 两套胜率口径。**尺子是歪的，回放生成 1,000 单就是 1,000 单歪读数。**

回放是「提速」，记分卡是「让读数可信」。提速不能救不可信的读数。

### 6.2 回放的正确姿势：预注册 + 一次性开盒

| 步骤 | 做法 |
|---|---|
| ① 预注册 | 写下：假设（如 capital_short 净期望 > 1%）、区间、判据、样本量门槛，**存进 docs/ 并锁定** |
| ② 跑一次 | 回放该区间，产出样本 |
| ③ 入档 | 结果写进审计文档，**无论好坏** |
| ④ 禁回头 | **不允许**基于该区间结果改代码再重跑同一区间（可换**未用过的**新区间） |

这条纪律比任何技术手段都重要，因为它防的是你自己（§4）。

### 6.3 分层验证，别一锅端

| 层 | 手段 | 说明 |
|---|---|---|
| 选股层 | **只能实盘积累** | §2，回放不可用；且需从今天起落 `watchlist_snapshot` 才有未来 |
| 分析/决策层 | 回放可加速 | 行情类判据（trend / capital 短周期）优先 |
| 结果验证 | 回放 + 扣成本 + 涨停不可成交过滤 | 见 §6.4 |

### 6.4 回放必须加实盘摩擦，否则高估

- 扣 0.25% 成本（同 G4）；
- **涨停/一字板不可买入** ⇒ 该票不计入 buy 样本（回放假设收盘价成交，实盘买不到）；
- **跌停不可卖出** ⇒ 持有期被迫延长；
- 滑点按流动性（成交额）分档。

这一条对 trend 策略影响最大——它专挑强势股，回放读数含水分最多。
而 `trend_short` 回放已是 **-1.68%**、`trend_ultrashort` **-1.57%**（成熟样本），
扣掉水分只会更差。

### 6.5 样本独立性：200 单 ≠ 200 个证据

同一天推荐 30 只票，这 30 单共享同一市场环境，**高度相关**。
有效样本量 ≈ 批次数 × 独立度，不是 单数。

⇒ 回放必须**跨越多个市场 regime**（牛 / 熊 / 震荡各 ≥ 1 段），
否则 200 单全落在同一环境里，sample size 虚高。`market_regime` 判定已有
（`analysis-engine/src/market_regime.rs`），可按 regime 分桶。

## 7. 一句话

> 你担心的「数据变脏」已经被 `analysis_kind` / `synthetic` / `as_of_date` + 闭环
> `as_of_date IS NULL` 挡住了——这块你做得比你以为的好。
>
> 真正挡路的是另一件事：**回放能重造「当时的判断」，重造不了「当时看到的票」。**
> 而候选池里最容易偏的那一路（自选股）恰好没有历史快照。
>
> 所以回放可以让你更快地知道「给定这些票，判断对不对」；
> 但它给不了「系统能不能替我选出对的票」——后者只能靠实盘，一天一天攒。
