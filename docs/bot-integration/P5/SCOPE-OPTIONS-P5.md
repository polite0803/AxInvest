## 2. 候选 A — 多 Bot 协作运行时（OMB `runtime-contract.md` / `team-sharing.md` 剩余语义）

### 2.1 要解决什么

P3 已落地静态 DAG 编排（`steps_json` + 拓扑 runner）与动态委派树（`root/parent/depth`，depth≤3），部门 Chief 派工与 consult 也已可用。**剩下的不是「能不能协作」，而是三处「协作发生后怎么收尾」：**

| # | 缺口 | 现状证据（本轮读取） | OMB 语义 |
|---|---|---|---|
| A1 | 事故线程与自动重试 | `bot_assignments` 字段止于 `status/result_text/error_code/error_detail`（`entities/src/bot_assignments.rs:16-59`），**无 retry 计数、无事故线程指针**；P3 `GAP-P3.md` G-P13 明写「不做自动事故线程与 ≤2 重试」 | 被委派方 run 失败上报收口 Bot 的「待处理问题」线程，重试 ≤2 次（`team-sharing.md`、`team-incidents.md`） |
| A2 | 线程 `openedBy` 归属 | 全仓 `opened_by`/`openedBy` **零命中**；`conversations` 无该列（`entities/src/conversations.rs`）；`list_bot_threads`（`src-tauri/src/commands/bot.rs:487`）只按 `bot_id` 过滤 | 线程记录含 `openedBy{botId,name,threadId,at,kind}`；列线程时标「opened by」，Chief 可关闭他人开的闲置线程 |
| A3 | Bot 群聊 / rooms | 仅 `fleet_messages`（办公室场景）；P3 `GAP-P3.md` G-P16 判「不涉编排」 | rooms：多 Bot 同室对话、成员与可见性 |

### 2.2 预估人日（拆两档）

| 档 | 内容 | 人日 |
|---|---|---|
| **A-min** | A1 事故线程 + 重试上限（含新表/新列、重试守护、通知与线程回执）+ A2 `openedBy` 列与列表/关闭 | **7–10**（A1 5–7，A2 2–3） |
| **A-full** | A-min + A3 rooms 只读列表与成员 | 13–18（rooms 6–8） |

校准：P4 两条切片（2 新表 + 6 命令 + 34 UI 键 + 5 码 ×11 语言）为 17.5–18 人日。A1 的新表与新命令量级略小于 P4-b，但重试守护的并发与幂等测试更重，故 5–7。

### 2.3 依赖

- P3 的 run / assignment 状态机与 `workflow_run_id/step_key`（A1 的事故线程要落在正确的 root 线程）。
- P2-a 的 `Notification.botId` 与 `agent-done` 推送（事故上报复用通知，不建新通道）。
- P2-a 审批解析 `resolve_effective_permission`（**重试必须沿用原档，不得升级**）。
- 若做 A2：`conversations` 是共享表，改动波及全部既有的会话列表查询与 DTO。

### 2.4 风险

| 风险 | 说明 | 缓解方向 |
|---|---|---|
| **成本与副作用翻倍** | P3 G-P13 的原话就是因此不做自动重试；一次失败重试 = 再跑一轮模型与工具 | 硬上限 2 次、只重试「未产生工具副作用」的失败（或按错误码白名单）、重试次数落库可审计 |
| **递归派工** | 事故线程本身是一个 Bot 线程，若它再触发委派，会与 P3 depth cap、P4 部门配额叠加成难推理的图 | 事故线程只允许「通知 + 人工重试 + 收口人裁定」，禁止在其内自动派工 |
| **rooms 变成第二套 IM** | 与 `fleet_messages`、`bot_threads` 语义重叠，成员/可见性/未读/通知四件都要重做 | 单独立项；先只做「只读列表 + 跳转」，不做实时消息 |
| **A2 迁移面** | 共享表加列 → 所有会话查询的 DTO 与前端列表回归 | 可空列 + 默认 owner=当前 bot，先只用于 Bot 侧栏展示 |

### 2.5 与 P1–P4 的关系

复用 P1 的线程归属、P2-a 的通知与审批、P2-b 的部门与委派、P3 的树形状态机、P4 的配额校验与「独立请求表」形态（事故记录可参照 `bot_input_requests` 的四态表写法）。**不改任何已冻结语义**：`waiting` 仍是依赖阻塞，`needs_input` 仍是交互待答，二者都不复用为「事故」。

## 3. 候选 B — 费用 / Token 配额

### 3.1 要解决什么

让「这个 Bot / 这个部门这周花了多少、还能花多少」可见，并在超限时**停住新建的运行**（不是精确扣费）。

| 现状 | 证据（本轮读取） | 结论 |
|---|---|---|
| 计价与预算已有，但只是会话/日级 | `src-tauri/src/commands/agent/pricing.rs:33-38`：`BudgetConfig{max_tokens_per_turn, max_cost_per_day_usd, max_cost_per_session_usd}` | 有计价函数，**无 Bot 维度** |
| 原始用量有列，但归属靠 join | `messages`：`token_count/prompt_tokens/completion_tokens/cache_creation_tokens/cache_read_tokens`（`entities/src/messages.rs:16-18,35-36`）；`agent_sessions.total_tokens`（`:21`）；`conversations.bot_id`（P1 已加，`conversations.rs:58`） | 可 join 出数字，但见下一条 |
| 委派/编排无用量列 | `bot_assignments` 无 token/cost 字段 | 跨 Bot 的执行无法归因到「谁花的」 |
| 会话会被清理 | P4 `PLAN-P4.md:419` 原文：「例程会话还会被清理」 | **事后 join 会越查越少**，账本必须写入时固化 |

### 3.2 预估人日（8–12，P4 原估）

| 卡 | 内容 | 人日 |
|---|---|---|
| B1 | 用量账本表 + 三个写入点（交互轮 / 委派轮 / 编排步骤），写入时固化 bot、部门、run、模型、in/out token、估算费用 | 3–4 |
| B2 | 解析与校验层（复用 P4 的「只收紧」解析形态），超限只拦「新建运行」 | 2–3 |
| B3 | 命令 + 错误码 + 侧栏/部门弹窗用量页签 | 2–3 |
| B4 | Rust 测试 + e2e + 契约/i18n 门禁与台账 | 1–2 |

### 3.3 依赖

- `pricing.toml` 与 `BudgetConfig`（计价口径来源；无价模型的 heuristic fallback 要写进 UI 说明）。
- P4 的配额解析器形态（`min` 只收紧、一次解析 task-local 下发）——**这是 B 最便宜的地方：解析层已存在，加一个维度而不是重造一层**。
- 非交互轮的会话生命周期（例程/委派/编排），是最大的不确定项。

### 3.4 风险

| 风险 | 说明 | 缓解方向 |
|---|---|---|
| **只能事后熔断** | 用量要等一轮结束才知道，无法在触发前精确判断 | 明确口径「超限停新建 run/轮」，UI 写「估算」不写「账单」 |
| **跨 provider 计价不统一** | 缓存读写 token、无价模型、不同 provider 的计费差 | 只做本地估算表；费用列标注「按 pricing.toml 估算」；不做对账承诺 |
| **账本与清理竞态** | 会话清理任务与账本写入并发 | 账本只写不改、与会话生命周期解耦；清理任务不触账本 |
| **并发写原子性** | 多 Bot 并发完成时同表写入 | 单条 INSERT（append-only），汇总走查询 |

### 3.5 与 P1–P4 的关系

P4-a 的配额表与解析层是它的地基；P4-b 与它无关；P3 的编排常量默认值不动（费用维度是**覆盖层**，与 P4 同一条「只收紧」原则）。不改 P3 的 2/900/12，也不改 P2-b 的 4/8/300。

## 5. 推荐组合与理由（候选，待拍板）

### 5.1 推荐

**P5 主体 = B（费用/Token 配额，8–12）+ C1（技能预设导入，4–5），合计约 12–17 人日，两条互不依赖的纵向切片，三人并行 5–6 个工作日。**

理由（按权重）：

1. **B 的边际成本最低。** P4 刚落地「只收紧」的配额解析层与 task-local 下发路径，B 只是在这条路上加一个费用维度，而不是新造一层。换个批次做，这层上下文就凉了。P4 也已把 B 写成「P5」的默认归属（`PLAN-P4.md:60`）。
2. **B 的用户价值是「可见」而非「精确」。** 8–12 人日换「哪个 Bot 在烧钱」的可见性与超限熔断，对 8–12 人的团队是刚需；口径写清「估算」即可，不必追平 provider 账单。
3. **C1 与 B 零交集、可并行**，给 Bot 侧栏补上「技能」页签，是本批唯一的新用户可见面，且没有运行时风险。
4. **A 不进本批。** 它的三个子项都不满足「一个可独立上线的纵向切片」：A1 的自动重试是成本放大器（P3 已因此判不做）、A3 rooms 等于第二套 IM。协作需求真实出现时再单独立项，且先只做 A-min（7–10）。
5. **C3（记忆写入）建议排在 P5-b 或 P6 首位，而不是本批。** 它是三条里用户价值最高的闭环缺口，但它需要先裁决「记忆写入属哪一档审批」，这条裁决本身要用户拍板；与 B 同批会把一个待裁决项塞进关键路径。

**备选（若用户更看重「Bot 能改自己的记忆」）：用 C3 替换 C1**，总量不变（12–17 人日），代价是本批多一个待裁决点、少一个零风险的新界面。

### 5.2 明确不推荐

- **A + B 同批**：13–20 人日且两条都在运行时层，回归面叠加，容易重演「收口靠补台账」。
- **C 三项打包一次上线**：12–16 人日看似一坨，但 C2（对外面）与 C3（写入面）风险性质不同，打包会让门禁口径混在一起。
